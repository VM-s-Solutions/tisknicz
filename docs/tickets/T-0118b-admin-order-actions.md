# T-0118b — Admin order detail + money/state action surfaces (`/dashboard/admin/orders/[orderId]`)

## Context

T-0118b is **slice 2 of the T-0118 split** and the **first ticket of the second admin-frontend PR** (PR 2 bundles b + c in risk-ascending order b → c; slice a shipped alone in PR 1). The split, locked at the 2026-06-15 deliberation: **T-0118a** (shell + admin login + overview KPIs + all the read lists — the verification harness), **T-0118b** (this — order detail + the three money/state action surfaces), **T-0118c** (ops + control-plane: outbox retry/ack, payout management, country config, GDPR delete). Each slice is one ticket. b and c assert their effects against a's read lists (e.g. after a refund here, a's `/dashboard/admin/orders` list shows the order in `Refunded`; the audit entry surfaces in a's audit-log view).

This slice extends T-0118a's all-orders list with the **order detail route** (`/dashboard/admin/orders/[orderId]` — full order snapshot + the order's audit trail, US-admin-0009 AC-2) and bolts on the three admin **write surfaces** that the order-cleanup backend bundle (T-0105/T-0106/T-0107) shipped endpoints for but no UI:

- **REFUND** (US-admin-0008) — `POST /api/v1/admin/orders/{id}/refund`, `RefundOrderRequest { amountMinor, reason, acknowledgePostPayout }` → `RefundOrderResponse`. Money moves. Rendered as a **modal** with the disabled-button-while-pending idempotency lock (the T-0087b precedent extended for a money path — see §A.1).
- **MANUAL STATE CHANGE** (US-admin-0010) — `POST /api/v1/admin/orders/{id}/state`, `ChangeOrderStateRequest { targetState, reason }` → `ChangeOrderStateManuallyResponse`. State machine via admin command. Rendered as a **modal** carrying the mandatory ≥10-char reason field (T-0107 Validator). The transition allow-list is **backend-enforced** (`ManualOrderTransitionPolicy`); the UI offers candidate targets and surfaces the `order.manualTransition.*` codes the policy returns.
- **DISPUTE open + resolve** (US-admin-0011) — `POST /api/v1/admin/orders/{id}/dispute` (`OpenAdminDisputeRequest { category, description }` → `OpenDisputeResponse`) and `POST /api/v1/admin/orders/{id}/dispute/resolve` (`ResolveDisputeRequest { outcome, resolutionNotes }` → `ResolveDisputeResponse`). Resolve is an **inline structured form** (outcome dropdown + resolution notes), per the locked decision (§A.3) — distinct from the two money/state modals.

Every action follows the same wire discipline established by T-0087b's maker action bar: a Client Component island POSTs through an `apiFetch`-wrapped admin helper, surfaces the backend's `BusinessErrorMessage` code through the cs-CZ catalog, and calls `router.refresh()` on success so the Server Component re-renders against the real row (no optimistic UI, no client-side state mirroring). The frontend owns **zero** business rules: the refund state gate, the manual-transition allow-list, and the dispute parenthesis-state semantics all live in the backend (T-0105/T-0106/T-0107 domain layer); this slice renders inputs and surfaces verdicts.

**Contract reality (read-only consumer, NO NSwag regen).** The admin client `admin-api.v1.ts` was already regenerated by T-0105/0106/0107/0111 — all four command methods (`refund`, `dispute`, `resolve`, `state`) and their request/response shapes exist in the generated client today (verified). This slice imports them; it does **not** touch `lib/api-client/`. The pre-commit hook would block an edit anyway.

**Detail-view boundary (scope finding — log a follow-up, do NOT add backend here).** There is **no admin order-detail DTO** and **no order-scoped audit-trail endpoint** in the generated client. T-0111 shipped the cross-tenant *list* (`AdminOrderListItemDto`) and the *global* audit-log query (`auditLog(...)`, filterable by `targetEntity` + an order id passed through the `actionCode`/free filters — see §C.2). The "full order detail" this route renders is therefore **bounded by what those two reads carry**: the `AdminOrderListItemDto` fields (orderNumber, state, country, totalAmountMinor, currency, createdAt, makerId, makerName, customerEmail, productTitle, isActive) plus the order's audit entries from the audit-log query filtered to this order. Line items, the lifecycle timeline, the payout/VAT breakdown, attachments, and the message thread are **NOT** in this slice — the backend exposes no admin read for them. A thin **`GetAdminOrderDetail` query + DTO follow-up ticket** is logged in `docs/questions/open.md` (the maker/customer detail DTOs from T-0082 are owner-scoped and not reusable on the admin host). This slice ships the richest detail the current contract allows and labels the gap, rather than inventing a backend read in a frontend bundle.

Money + state movement through admin commands makes this slice **security_touching**. The boundary is backend (admin-audience JWT per ADR 0013, the allow-list policy, the refund gate, audit pipeline); the UI's security obligation is to never pre-authorize a forbidden action client-side and to surface every backend refusal loudly.

## Locked design decisions

Captured per `docs/process/deliberation.md`. The user locked the action-surface shapes at the 2026-06-15 split deliberation; the rest is PM-absorbed from the T-0087b action-bar precedent and the T-0118a shell.

### A. User-locked at the 2026-06-15 deliberation (non-negotiable)

1. **Refund = MODAL dialog with a money-grade idempotency lock.** Refund moves money, so it opens a confirm **modal** (UI primitive, never `window.confirm`) carrying three inputs: `amountMinor` (defaulting to the order's full `totalAmountMinor`, editable down for a partial — the backend caps at `RemainingRefundableMinor`), a required `reason`, and an `acknowledgePostPayout` **checkbox that renders only when the order's `state == Completed`** (the maker is already paid out — T-0105 AC-4 requires the flag, else `payment.refund.postPayoutAckRequired`). The submit button uses the **disabled-button-while-pending idempotency lock per T-0087b** (the action bar disables + shows a `Spinner` during the in-flight POST; a second click cannot fire — the partial-refund path has no idempotency key at MVP per T-0105 Risk, so this UI lock is the front-line guard the backend ticket explicitly defers to, ref Q-0018). Surfaces every `RefundOrder` error code: `payment.refund.invalidState`, `payment.refund.amountExceedsRemaining`, `payment.refund.postPayoutAckRequired`, `payment.refund.noProviderRef`. **Rejected:** inline refund form (a one-click money move with no modal friction invites fat-finger refunds — friction goes where the blast radius is, the T-0087b ship-confirm rationale); optimistic state flip (lies on a `Permanent` Comgate rejection — T-0105 AC-5 leaves the order byte-identical; `router.refresh()` is truthful); client-side amount validation beyond `> 0` (the remaining-refundable cap is backend math — surface `amountExceedsRemaining`, do not duplicate the arithmetic).

2. **Manual state change = MODAL with a mandatory reason; the allow-list is backend-enforced.** State change opens a **modal** with a `targetState` dropdown and a **mandatory `reason`** field (min 10 chars — T-0107 Validator `MinimumLength(10)`; the UI mirrors only the length hint, the backend re-validates). The dropdown lists candidate `OrderState` values; **the frontend does NOT implement the allow-list** (`ManualOrderTransitionPolicy` is Core.Domain — T-0107 §"the dropdown population endpoint, if wanted, is a T-0118 concern" but no such endpoint shipped, so the UI offers all non-current states and lets the backend refuse). A blocked transition surfaces the exact code the policy returns — `order.manualTransition.notAllowed`, `...useRefundOrder`, `...useOpenDispute`, `...useResolveDispute`, `...useMarkPayoutBatchCompleted`, `...paidRequiresProviderRef` — each mapped to a cs-CZ string that names the sanctioned action (e.g. "Použijte refundaci objednávky"). **Rejected:** client-side allow-list (re-implements the state machine in TypeScript — forbidden business logic that drifts on the first backend rule change, the T-0087b A.1 rebuttal); a free-form state setter (the backend itself rejected this in T-0107 Q4; the UI must not paper over it); optional reason (T-0107 makes it mandatory — the UI cannot submit without it).

3. **Dispute resolve = INLINE structured form (not a modal).** Resolving a dispute is the admin's considered triage decision, not a destructive one-click — so it renders **inline** on the detail page (visible only when the order is in `Disputed`) as a structured form: an `outcome` dropdown (`DisputeResolutionOutcome`: Refunded / Resumed / Cancelled) + a required `resolutionNotes` textarea (customer-visible — T-0106 §C.7; the label says so). Dispute **open** (admin transcribing a phoned-in dispute, US-admin-0011) is a secondary inline affordance with a `category` dropdown (`DisputeCategory`, all six allowed on the admin endpoint) + `description`. Both surface `order.dispute.categoryNotAllowed` / `order.dispute.notOpen` / `order.invalidTransition`. **Rejected:** modal for resolve (resolve is a reviewed decision after reading the audit trail in the same view — a modal that occludes the evidence is worse UX than an inline form beneath it); folding open + resolve into one control (they are mutually exclusive by state — open shows when not Disputed, resolve shows when Disputed; one capability = one surface).

### B. ADR + pattern-locked (no relitigation)

- **patterns.md §B.1 — Server Components by default.** `page.tsx` is a Server Component fetching the order row + audit entries on render; only the action surfaces (`order-actions.tsx`, `dispute-form.tsx`) are `'use client'` islands. No `useEffect` data fetching anywhere in the route.
- **patterns.md §B.4 + §B.16 — all calls via `apiFetch`-wrapped helpers** returning `Result<T, ApiError>`. New `lib/api-client-helpers/admin-orders.ts` (or extends T-0118a's admin-orders read helper) wraps `refund` / `state` / `dispute` / `resolve` plus the detail read.
- **patterns.md §B.14 + ADR 0024 — SSR cookie forwarding** for the detail + audit reads. ADR 0013 admin-audience enforcement stays backend-side; a customer/maker JWT cannot replay against the admin host.
- **ADR 0022 — NSwag is the contract.** No backend change in this slice → **no regen**; the four command methods + the two reads already exist in `admin-api.v1.ts` (T-0105/0106/0107/0111). `lib/api-client/` is never hand-edited.
- **ADR 0014 — every admin write is audited** by `AdminAuditPipelineBehavior` backend-side; this UI consumes the resulting audit rows in the detail's audit-trail panel. Per Q-0021 (ruled 2026-06-14), idempotent no-op re-calls still write a benign audit row — the UI does not assert "no second audit row".
- **patterns.md §B.5 + §B.17 + §B.18 — i18n + `parseErrorResponse`.** Every surfaced code has a parallel cs-CZ key; RFC7807 bodies flow through the existing parser. The **T8 gate is now LIVE** — a missing cs-CZ key fails CI, so every new `dashboard.admin.orderActions.*` and error key must exist.
- **patterns.md §B.10 — `formatCzk`** for `totalAmountMinor` + the refund amount display. No money math client-side (the remaining-refundable cap is backend-owned).
- **patterns.md §B.9 — `generateMetadata` branches title only on NotFound;** a missing/foreign order id → `notFound()` (the admin read returns one shape).

### C. PM-absorbed (no user input needed)

1. **Admin tone = vykání (V form).** The admin surfaces address the operator formally (PM default for the admin host — the two operators are addressed as "vy", consistent with the customer surface and distinct from the maker tykání). All `dashboard.admin.*` keys written vykání.
2. **Detail read composition.** The Server Component fetches the order row by filtering T-0111's `adminOrders(page:1, pageSize:1, ...)` to this order id is NOT possible (the list query has no id filter). The page instead reads the order via the same mechanism T-0118a's list-row click target uses — **deferred to the logged `GetAdminOrderDetail` follow-up if T-0118a did not already establish a single-order read**. Until that endpoint exists, the detail page hydrates the order header from the navigation state / the list row passed through, and reads the **audit trail** via `auditLog(page, pageSize, undefined, undefined, "order", undefined, undefined)` then filters/paginates to this order's `targetId` client-shapeable on the server. The audit-trail panel is the slice's load-bearing read; the order header degrades gracefully to the list-row fields. **This composition gap is the §Context detail-boundary finding — the follow-up ticket closes it cleanly.**
3. **SSR + force-dynamic + URL-state.** `export const dynamic = 'force-dynamic'` (T-0087a/T-0116 precedent — admin data is never statically cached). The audit-trail panel paginates via URL search params (no client pagination state), matching the T-0118a list precedent.
4. **All actions → POST → `router.refresh()`.** Success re-runs the Server Component against the new row (new state badge, new audit entries, the refund reflected, the dispute resolved). One mechanism, always truthful, doubles as the stale-action recovery path.
5. **Pending/disabled handling, per action.** Each action surface disables its submit + shows the `Spinner` primitive during the in-flight POST; failure re-enables and renders an inline `Alert variant="error"` with the mapped i18n message (T-0087b §C precedent). The refund modal's lock is the strictest (money path, no backend idempotency key — A.1).
6. **No blob download in this slice.** This slice has no CSV/PDF/label download (those are T-0118c payout CSV + invoice PDF). The `apiFetch parse:'blob'` discipline is a T-0118c concern; nothing here touches the NSwag `Promise<void>` file gap.
7. **i18n namespace.** New keys under `dashboard.admin.orderActions.*` (section headings, refund modal copy incl. the irreversibility-of-money note + post-payout-ack warning, state-change modal copy, dispute open/resolve labels, outcome/category dropdown option labels, audit-trail panel headings) plus the error-code keys for every `payment.refund.*`, `order.manualTransition.*`, and `order.dispute.*` code surfaced (if any are already present from T-0105/0106/0107's i18n additions, verify and reuse — do not duplicate).
8. **Reuses T-0118a's shell/nav.** The route nests under the `(admin)` route group whose real shell (header, sidebar, audience-guarded layout) T-0118a builds — this slice adds only the detail route + its islands, not chrome.

## Scope

- **`frontend/src/app/(admin)/dashboard/admin/orders/[orderId]/page.tsx`** — NEW Server Component. - **`.../[orderId]/dispute-form.tsx`** — `'use client'` island. ## Acceptance criteria

- **AC-1** Given an admin on the admin host, when they visit `/dashboard/admin/orders/{orderId}` for an existing order, then the page renders server-side (`page.tsx` has no `'use client'`; reads via SSR cookie forwarding) showing the order header (number, state badge, country, total via `formatCzk`, maker name, customer email) and the order's audit-trail panel. No `useEffect` data fetching anywhere in the route.
- **AC-2** Given a non-existent or foreign order id, when visited, then Next.js `notFound()` renders (one shape; title branch per §B.9).
- **AC-3** Given the refund control, when the admin opens it, then a **modal** (not `window.confirm`) shows `amountMinor` (defaulted to `totalAmountMinor`, editable), a required `reason`, and — **only when `state == Completed`** — an `acknowledgePostPayout` checkbox with the post-payout warning copy. Submitting POSTs `refund` with the entered body.
- **AC-4** Given a successful refund, when the POST returns 200, then the modal closes, `router.refresh()` re-renders the page, and the order shows the new state (`Refunded` on a full refund; unchanged with the partial reflected). The submit button was **disabled with a Spinner during the in-flight POST** and a second click could not fire (idempotency lock).
- **AC-5** Given a refund that the backend rejects (`payment.refund.amountExceedsRemaining`, `...invalidState`, `...postPayoutAckRequired`, `...noProviderRef`, or a Comgate `Permanent` error), when the POST fails, then an inline i18n-keyed `Alert` renders the mapped Czech message (no raw code, no silent failure), the button re-enables, and no client-side state was optimistically flipped.
- **AC-6** Given the state-change control, when opened, then a **modal** shows a `targetState` dropdown and a **mandatory `reason`** field; the dropdown does **not** implement the allow-list (offers non-current states); submit POSTs `state` with `{ targetState, reason }`. A `reason` under 10 chars cannot submit (UI hint mirrors the backend Validator).
- **AC-7** Given a blocked manual transition, when the POST returns 409 with a `order.manualTransition.*` code, then the inline `Alert` renders the mapped Czech string that **names the sanctioned action** (e.g. `useRefundOrder` → "Použijte refundaci objednávky"); the order is unchanged; `router.refresh()` reconciles. A successful transition closes the modal and refreshes to the new state badge.
- **AC-8** Given an order in `Disputed`, when the detail renders, then the **inline dispute resolve form** shows (outcome dropdown: Refunded / Resumed / Cancelled; required `resolutionNotes` textarea labelled customer-visible); submitting POSTs `resolve`; on 200 `router.refresh()` shows the restored/terminal state and the resolved dispute. A non-Disputed order shows the inline **open-dispute** form instead (category + description), never both.
- **AC-9** Given a dispute action the backend rejects (`order.dispute.categoryNotAllowed` on open — though the admin endpoint allows all six categories, so this is defensive; `order.dispute.notOpen` on resolve; `order.invalidTransition`), when the POST fails, then the mapped i18n `Alert` renders inline and the order is unchanged.
- **AC-10** Given any of the three actions, when it succeeds, then the order's audit-trail panel (after the `router.refresh()`) shows the new audit entry (action code `order.refund` / `order.manualStateChange` / dispute resolve), who/what/when — proving the read harness (T-0118a / T-0111 audit-log query) reflects the write. (Per Q-0021, an idempotent no-op re-call also writes a benign audit row; the UI does not assert its absence.)
- **AC-11** Given the contract, when the slice is built, then **no file under `frontend/src/lib/api-client/` is modified** (the four command methods + the audit-log read pre-exist from T-0105/0106/0107/0111); no NSwag regen runs; the pre-commit hook passes.
- **AC-12** Hygiene + i18n gate: zero `any`, zero unsafe `!`, zero `console.*`, zero hardcoded Czech outside `cs-CZ.ts` (admin vykání), every surfaced `payment.refund.*` / `order.manualTransition.*` / `order.dispute.*` code has a cs-CZ key (**LIVE T8 gate — a gap fails CI**), responsive at 375/768/1280 (modals usable on mobile), `npm run lint` + `npm run build` clean, `node scripts/check-consistency.mjs` exit 0.

## Alternatives Considered

- **Option A — Refund as an inline one-click form (no modal).** *Rejected per A.1* — refund moves real money through Comgate with no UI undo; a frictionless inline submit invites fat-finger refunds. The modal + disabled-button lock is the front-line guard the backend (T-0105) explicitly defers to (no partial-refund idempotency key at MVP; Q-0018 open). Friction goes where the blast radius is — the T-0087b ship-confirm rationale applied to money.
- **Option B — Client-side manual-transition allow-list (compute valid targets in TypeScript).** *Rejected per A.2* — re-implements `ManualOrderTransitionPolicy` (Core.Domain) in the frontend; forbidden business logic that drifts the instant a backend rule changes. The UI offers candidate targets and surfaces the backend's verdict + the sanctioned-command hint. (T-0087b A.1 rebuttal, transplanted to the admin tool.)
- **Option C — Optimistic state flip after any action.** *Rejected per A.1/A.2* — lies on failure (`Permanent` refund rejection leaves the order byte-identical per T-0105 AC-5; a blocked transition leaves it unchanged per T-0107). `router.refresh()` is the truthful, single-source reconciliation and doubles as stale-action recovery.
- **Option D — Dispute resolve in a modal (uniform with refund/state).** *Rejected per A.3* — resolve is a reviewed triage decision made after reading the order's audit trail/evidence in the same view; a modal occludes exactly the context the admin needs. The inline structured form keeps the evidence and the decision on one screen. (Refund/state stay modal because they are quick, high-blast-radius, context-independent actions.)
- **Option E — Invent a `GetAdminOrderDetail` backend read in this slice to render line items / timeline / breakdown.** *Rejected* — this is a frontend bundle; adding a backend query violates the slice's read-only-consumer contract and the brief's "log a follow-up, don't add backend" rule. The detail renders the richest view the current contract (list DTO + audit-log query) allows and logs the gap for a clean backend ticket. The T-0082 maker/customer detail DTOs are owner-scoped and not reusable on the admin host.
- **Option F — Fold dispute open + resolve into one toggle control.** *Rejected per A.3* — they are mutually exclusive by state (open when not Disputed, resolve when Disputed) and are distinct capabilities; one capability = one surface keeps each form's validation + error surface clean.
- **Option G — Skip the audit-trail panel (just the order header + actions).** *Rejected* — US-admin-0009 AC-2 names the audit-trail tab as the admin detail's distinguishing feature, and AC-10 needs it to prove each write reflects in the read harness. The audit-log query (T-0111) is the one rich read the contract offers for this route; omitting it would make the detail thinner than the list.

## Risk / mitigation

- **Partial-refund double-submit on a slow network** (no backend idempotency key — T-0105 Risk; Q-0018 open). *Mitigation:* the modal's disabled-button-while-pending lock (A.1) is the front-line guard; the remaining-refundable cap bounds damage even if a click slips through (the second POST exceeding remaining → `amountExceedsRemaining`). Pinned by AC-4.
- **Stale action** (order state changed in another tab; admin clicks an outdated action). *Mitigation:* the backend re-validates every command (`payment.refund.invalidState`, `order.manualTransition.*`, `order.dispute.notOpen`); the inline `Alert` + `router.refresh()` reconcile. Pinned by AC-5/AC-7/AC-9.
- **Detail-read composition gap** (no admin order-detail DTO; the header degrades to list-row fields until the follow-up ships). *Mitigation:* the audit-trail panel (the load-bearing read) is fully available via the audit-log query; the §C.2 composition + the logged follow-up make the gap explicit and bounded, not silent. The build does not depend on a non-existent endpoint (no-mocks rule honoured — the route reads only endpoints that exist).
- **Missing i18n key at runtime** (the surfaced-code parity pattern). *Mitigation:* the LIVE T8 gate fails CI on any missing cs-CZ key; AC-12 verifies all three error-code families resolve.
- **Security: a forbidden action pre-authorized client-side.** *Mitigation:* the UI implements **no** allow-list / refund-gate / state-machine; the backend (admin-audience JWT per ADR 0013 + the policy/gate/parenthesis-state guards) is the sole authority. The slice's only security obligation is to surface refusals loudly and never optimistically flip — both pinned by ACs. Security review applies at PR per `security_touching: true`.
