# T-0131 — SEO surface: sitemap.ts + robots.ts + OpenGraph/Twitter/canonical metadata

## Context

T-0131 is the **second ticket in the public-polish bundle** (T-0130 static content + T-0131 SEO), branch `feat/public-polish-bundle`, user-locked 2026-06-20. Both ship under one PR. T-0130 lands the four static public routes (`/jak-to-funguje`, `/pro-makery` with real marketing prose; `/vop`, `/gdpr` as approved-text-pending placeholder shells); T-0131 makes the whole public surface discoverable and shareable: a Next.js App-Router `sitemap.ts`, a `robots.ts`, and OpenGraph/Twitter/canonical metadata on the four indexable page types.

This ticket adds **zero new pages and zero business logic** — it is pure presentation-layer metadata wiring on top of the catalog reads that already exist (T-0046 catalog list, T-0047 maker profile, T-0048 product detail). The frontend stays a pure presentation layer per CLAUDE.md: `sitemap.ts` and `robots.ts` are Next.js `MetadataRoute` conventions (not hand-rolled XML), the dynamic sitemap enumeration reuses the existing `lib/api-client-helpers/catalog.ts` reads (no new endpoint, no business logic), and the OG/Twitter objects extend the `generateMetadata` already on each page rather than introducing new metadata machinery.

The four indexable page types already carry `generateMetadata` (title + description): `/katalog` (`frontend/src/app/(public)/katalog/page.tsx`), `/katalog/[slug]` (maker profile), `/produkt/[productId]` (product detail). **The landing page (`frontend/src/app/page.tsx`) is the one exception — it currently has NO `generateMetadata`** (it inherits the root-layout `metadata` from `frontend/src/app/layout.tsx`). T-0131 adds a `generateMetadata` to the landing page so it gets the same OG/Twitter/canonical treatment as the others. For the three pages that already have `generateMetadata`, T-0131 **adds** the `openGraph` / `twitter` / `alternates.canonical` objects to the returned `Metadata` (the title/description stay; OG strings reuse the existing meta description per the PM-absorbed default — no new i18n keys for OG copy).

**Absolute-URL base gap (must be resolved here).** OG `url`, Twitter cards, canonical, and the sitemap/robots all need an absolute origin. There is currently **no `metadataBase` and no site-URL env var** in the frontend (`frontend/src/app/layout.tsx` has none; only `NEXT_PUBLIC_API_PUBLIC_BASE_URL` exists, and that is the API host, NOT the site origin). T-0131 introduces a single `NEXT_PUBLIC_SITE_URL` (default `https://makables.cz`, localhost in dev), reads it in one place (`frontend/src/lib/seo/site-url.ts`), sets `metadataBase` on the root layout so Next resolves relative OG URLs, and uses the same helper for sitemap/robots/canonical. This is the only env-touching change and it is non-secret (`NEXT_PUBLIC_*` is allowed in the client bundle per CLAUDE.md Security).

No new `BusinessErrorMessage` codes, no backend change, no migration, no NSwag regen (no API contract change — the dynamic sitemap reuses the existing catalog reads). New i18n keys ship only if a new user-facing string is introduced; per the PM-absorbed default the OG strings reuse the existing meta description, so the only candidate new strings are the landing-page meta title/description (the landing page has none today) — those get cs-CZ keys (T8 i18n gate is LIVE; every new public string must be keyed or CI fails).

## Locked design decisions

Captured per `docs/process/deliberation.md`. The user locked the public-polish bundle on 2026-06-20 (T-0130 content shape + T-0131 SEO scope). PM-absorbed decisions follow from the Next.js MetadataRoute conventions, the existing T-0047/T-0048 `generateMetadata` precedent, and CLAUDE.md frontend rules.

### A. User-locked at bundle lock 2026-06-20 (non-negotiable)

1. **`sitemap.ts` / `robots.ts` are Next.js `MetadataRoute` conventions, not hand-rolled XML.** `frontend/src/app/sitemap.ts` exports a default function returning `MetadataRoute.Sitemap`; `frontend/src/app/robots.ts` exports a default function returning `MetadataRoute.Robots`. Next renders `/sitemap.xml` and `/robots.txt` from these. **Rejected:** a hand-written `public/sitemap.xml` static file (goes stale; can't enumerate dynamic routes; no type safety) and a custom route handler emitting XML by hand (reinvents what the convention gives for free).

2. **`robots.ts` allows all at MVP — no `Disallow`.** Single `rules: { userAgent: '*', allow: '/' }` plus a `sitemap` reference. The public surface is meant to be fully indexable at launch; the authenticated `(customer)` / `(maker)` / `(admin)` dashboards are not in the sitemap and are behind auth, so no `Disallow` is needed to keep crawlers out of them (they 401). **Rejected:** disallowing `/dashboard` / `/admin` explicitly (defensive but unnecessary — those paths require auth; listing them in robots.txt actually *advertises* their existence to scrapers).

3. **OG metadata extends the existing `generateMetadata` on the four indexable page types** (landing `/`, `/katalog`, `/katalog/[slug]`, `/produkt/[productId]`). Add `openGraph { title, description, url, type }` + `twitter` (summary card) + `alternates.canonical`. **Rejected:** a wholesale rewrite of each page's metadata (loses the existing NotFound-safe title branching on the dynamic pages — see T-0047 nit #1 carried into `produkt`/`katalog/[slug]`); a single shared root-layout-only OG block (can't carry per-page title/description/url; static OG defeats the point of sharing a specific maker/product).

4. **Sitemap dynamic-enumeration decision is the implementer's call, flagged.** The static routes (`/`, `/katalog`, `/jak-to-funguje`, `/pro-makery`, `/vop`, `/gdpr`) are always enumerated. The dynamic routes (`/katalog/[slug]` maker profiles, `/produkt/[productId]` products) **should** be enumerated from the catalog reads (`getPagedMakers` for slugs; the per-maker product ids). **If that enumeration is heavy or fragile at MVP** (it requires walking every catalog page to collect slugs, and there is no bulk "all product ids" read), a **static-routes-only sitemap with a `// TODO(T-NNNN)` follow-up note + a Q-item is acceptable for MVP**, and the implementer flags which path was taken in the PR description. Default preference: enumerate makers (one paged walk of `getPagedMakers`, capped), and **defer product-id enumeration** (no bulk read exists — see Technical notes). **Rejected:** blocking the whole ticket on a new backend "sitemap feed" endpoint (out of scope for a frontend-only polish ticket; would force a backend change + NSwag regen).

### B. ADR-locked (no relitigation)

- **ADR 0005 (route groups + public surface).** The indexable pages live in the public route group. Route groups (`(public)`) do **not** affect URL paths — `/katalog`, `/jak-to-funguje`, etc. resolve identically regardless of the folder. `sitemap.ts`/`robots.ts` live at `frontend/src/app/` root (App-Router convention — they are NOT route-group-scoped). The sitemap enumerates **URL paths**, not folders.
- **CLAUDE.md frontend rules.** Server Components by default — `sitemap.ts`/`robots.ts` run server-side (build or request time); the `generateMetadata` functions are already server-side. No `'use client'`, no `useEffect` data fetching. All data via `lib/api-client-helpers/` (the catalog reads) — no DB SDK. All user-facing strings via cs-CZ i18n (T8 gate).

### C. PM-absorbed (no user input needed)

- **Site-URL base helper.** New `frontend/src/lib/seo/site-url.ts` exporting `SITE_URL` (reads `NEXT_PUBLIC_SITE_URL`, default `https://makables.cz`, `http://localhost:3000` only when the env var is unset AND `NODE_ENV !== 'production'`) and a `canonicalUrl(path: string)` helper that joins `SITE_URL` + a leading-slash path. Single source of truth for every absolute URL in the SEO surface — mirrors the centralisation pattern of `buildProductImageUrl` in `catalog.ts`.
- **`metadataBase` on the root layout.** Set `metadata.metadataBase = new URL(SITE_URL)` in `frontend/src/app/layout.tsx` so Next resolves relative `openGraph.url` / canonical values against the canonical host. Without this, relative OG URLs resolve against `localhost` in dev and warn in build.
- **OG type per page:** `website` for landing + `/katalog`; `profile` for `/katalog/[slug]`; `product` (via `og:type` string `'product'`, set through `openGraph.type` — Next types it as `OpenGraphType`) for `/produkt/[productId]`. Twitter card type: `summary` everywhere (no large-image asset at MVP — see OG-image decision).
- **OG-image decision: text-only OG at MVP (no `images` array).** No brand OG image asset exists in `frontend/public/`. A text-only OG (title + description + url) is valid and renders a clean text card; the `images` field is omitted with a `// TODO(T-NNNN)` note. When a brand OG image lands, add it once to the `site-url.ts` helper (default OG image) and every page inherits it via `metadataBase`. Flagged in the PR description.
- **Canonical = the page's own absolute URL.** Landing → `SITE_URL`; `/katalog` → `SITE_URL + '/katalog'` (canonical is the unfiltered catalog URL — filter query params are NOT part of the canonical, so every filtered view points back to the canonical catalog; prevents duplicate-content dilution across filter combinations); `/katalog/[slug]` → `SITE_URL + '/katalog/' + slug`; `/produkt/[productId]` → `SITE_URL + '/produkt/' + productId`.
- **OG strings reuse existing meta.** `openGraph.title` / `twitter.title` reuse the page's computed `title`; `openGraph.description` / `twitter.description` reuse the page's computed `description`. No new i18n keys for OG copy. The only new keys are the landing-page meta `title` + `description` (the landing page has no `generateMetadata` today; the root-layout default is a literal, not a key).
- **NotFound-safe metadata preserved on dynamic pages.** The existing `produkt`/`katalog/[slug]` `generateMetadata` branch the title on `result.error.type === 'NotFound'` to avoid telling indexers a transient backend error means the entity doesn't exist (T-0047 nit #1). T-0131 keeps that branch and only **adds** the OG/canonical objects inside both the success and the error-fallback return paths (the canonical for a NotFound is still the requested URL — a 404 page is not indexed, but the canonical stays consistent).
- **Sitemap `changeFrequency` / `priority`:** static pages `priority` 0.8 (landing 1.0), `changeFrequency: 'monthly'` for legal/info pages, `'daily'` for `/katalog`; dynamic maker pages `priority` 0.6, `'weekly'`. `lastModified: new Date()` at generation time (no per-entity `updatedAt` surfaced through the catalog reads at MVP — flagged).
- **Sitemap revalidation:** `export const revalidate = 3600` on `sitemap.ts` (regenerate hourly) so a freshly-listed maker appears within an hour without a redeploy; the static-only fallback can be fully static.

## Scope

### New files

- **`frontend/src/lib/seo/site-url.ts`** — `SITE_URL` const + `canonicalUrl(path)` helper. Reads `NEXT_PUBLIC_SITE_URL`. Single source of truth for absolute URLs across the SEO surface. JSDoc mirrors the `buildProductImageUrl` convention in `catalog.ts`.
- **`frontend/src/app/sitemap.ts`** — default-export `async function sitemap(): Promise<MetadataRoute.Sitemap>`:
  - Always enumerate the static routes: `/`, `/katalog`, `/jak-to-funguje`, `/pro-makery`, `/vop`, `/gdpr` (each as `{ url: canonicalUrl(path), lastModified, changeFrequency, priority }`).
  - Dynamic maker enumeration: walk `getPagedMakers({ country: 'CZ', page, pageSize })` page-by-page (cap total pages, e.g. ≤ 20 pages / 480 makers at MVP) collecting `slug` → `canonicalUrl('/katalog/' + slug)`. Implementer adds the slugs-only dynamic enumeration and leaves a `// TODO(T-NNNN)` for products, OR (if even the maker walk is judged heavy) ships static-only and flags it in the PR. - **`frontend/src/app/robots.ts`** — default-export `function robots(): MetadataRoute.Robots`:
  - `rules: [{ userAgent: '*', allow: '/' }]` (allow-all MVP, no `Disallow`).

  - `host: SITE_URL` (optional but harmless; canonical host hint).

## Alternatives Considered

- **Option A — Hand-written static `public/sitemap.xml`.** *Rejected per A.1* — goes stale the moment a maker registers; can't enumerate dynamic routes; no type safety; duplicates what `MetadataRoute.Sitemap` gives for free. The convention file regenerates on a revalidate window.
- **Option B — Custom route handler emitting sitemap XML by hand.** *Rejected per A.1* — reinvents the `MetadataRoute` serialization, risks malformed XML, and bypasses Next's built-in `/sitemap.xml` wiring. No upside over the convention.
- **Option C — Disallow `/dashboard` + `/admin` in robots.txt.** *Rejected per A.2* — those paths are auth-gated (a crawler gets 401, never content), so a `Disallow` adds no protection. Worse, listing them in a public `robots.txt` *advertises* the admin path to scrapers. Allow-all is the correct MVP posture; sensitive surfaces are protected by auth, not by robots directives (robots.txt is advisory, not a security boundary).
- **Option D — Single root-layout OG block (no per-page OG).** *Rejected per A.3* — a static OG can't carry a specific maker's name or a product's title/price into the share card; sharing a maker profile would render the generic site card. Per-page `generateMetadata` extension is the only way to get a meaningful share preview for catalog/maker/product URLs.
- **Option E — Block the ticket on a new backend "sitemap feed" endpoint (bulk maker slugs + product ids).** *Rejected per A.4* — turns a frontend-only polish ticket into a cross-stack backend change (new query + controller + NSwag regen), violating the one-PR-per-ticket bias toward the smallest slice. The existing `getPagedMakers` read covers maker enumeration; product-id enumeration is deferred with a flagged follow-up. Re-evaluate post-MVP if SEO indexing of individual products proves valuable enough to justify a bulk read.
- **Option F — Reuse `NEXT_PUBLIC_API_PUBLIC_BASE_URL` as the canonical site origin.** *Rejected per C.1* — that env var is the **API host** (`localhost:5104` in dev, the Public API host in prod), NOT the site origin (`makables.cz`). Canonical/OG URLs must point at the user-facing site, not the API. A dedicated `NEXT_PUBLIC_SITE_URL` keeps the two concerns separate and prevents a canonical that points at the backend.
- **Option G — Skip `metadataBase`, write absolute URLs everywhere by hand.** *Rejected per C.2* — without `metadataBase` Next warns at build and resolves relative OG URLs against `localhost`. Setting `metadataBase` once on the root layout lets every page emit relative-or-absolute OG URLs consistently and is the framework-blessed approach.
- **Option H — Large-image Twitter card with an OG image now.** *Rejected per C.4* — no 1200×630 brand asset exists in `frontend/public/`. Shipping a `summary` (text) card now is valid and clean; the large-image upgrade is a one-line change once the asset lands (tracked in the launch checklist). Inventing a placeholder image would ship a broken/ugly share card.
- **Option I — Canonical includes the catalog filter query params.** *Rejected per C.6* — every filter combination (`?category=...&city=...&page=...`) would become its own canonical, fragmenting link equity across hundreds of near-duplicate URLs. The unfiltered `/katalog` is the single canonical; filtered views point back to it. Standard duplicate-content hygiene.

- **The actual approved legal TEXT for `/vop` + `/gdpr`** — blocking pre-launch action item, logged as Q-0030 + a launch-checklist line. The page SCAFFOLDING ships in T-0130; T-0131 does not touch legal text.
- **Landing-page body hardcoded-string cleanup** — the landing `page.tsx` body has hardcoded Czech (hero copy, stat labels, step cards). Re-keying the body is T-0130's static-content concern (or a separate hygiene ticket); T-0131 only adds the `generateMetadata` function (which uses keys).
- **A backend bulk "all maker slugs / all product ids" read** — explicitly deferred per A.4 / Option E. Product-id sitemap enumeration waits on this; maker enumeration uses the existing paged catalog read.
- **JSON-LD / structured data (schema.org `Product`, `LocalBusiness`, `BreadcrumbList`)** — not at MVP. OpenGraph + canonical covers share previews + canonicalisation; rich-result structured data is a post-MVP SEO enhancement.
- **`hreflang` / multi-locale alternates** — Czech-only at launch per CLAUDE.md. No `alternates.languages`. Multi-country-ready architecture, CZ-only data/UI.
- **OG image asset + large-image cards** — text-only `summary` card at MVP (Option H). The brand OG image is a launch-checklist follow-up.
- **Per-entity `lastModified` from a real `updatedAt`** — the catalog reads don't surface an `updatedAt` at MVP; the sitemap uses generation-time `new Date()`. Surfacing real modification timestamps is a post-MVP refinement.
- **Sitemap index / pagination for > 50k URLs** — MVP maker counts are far below the 50k single-sitemap limit; a sitemap index is a scale concern for later.
- **Backend / NSwag** — no API contract change; no regen.

## Acceptance criteria

- **AC-1** Given a build, when `/sitemap.xml` is requested, then it returns a valid sitemap (`MetadataRoute.Sitemap` serialized by Next) containing the six static URLs (`/`, `/katalog`, `/jak-to-funguje`, `/pro-makery`, `/vop`, `/gdpr`), each as an absolute URL under `SITE_URL`.
- **AC-2** Given the catalog has published makers, when `/sitemap.xml` is generated and dynamic enumeration is enabled, then each maker's `/katalog/{slug}` appears as an absolute URL. *(If the implementer ships static-only per A.4, this AC is satisfied by the documented static-only decision + the PR flag; the sitemap must still be valid and contain the static set.)*
- **AC-3** Given the catalog read fails transiently, when `/sitemap.xml` is generated, then it does NOT 500 — it falls back to the static routes and returns a valid sitemap.
- **AC-4** Given a build, when `/robots.txt` is requested, then it allows all user agents (`User-agent: *` / `Allow: /`), has no `Disallow`, and references the sitemap at `{SITE_URL}/sitemap.xml`.
- **AC-5** Given the landing page (`/`), when its rendered `<head>` is inspected, then it carries `og:title`, `og:description`, `og:url` (= `SITE_URL`), `og:type=website`, a `twitter:card=summary`, and `<link rel="canonical" href="{SITE_URL}">`. The title/description come from the new i18n keys (no hardcoded literal).
- **AC-6** Given `/katalog`, when its `<head>` is inspected, then it carries OG (`type=website`, `url={SITE_URL}/katalog`), Twitter summary, and a canonical equal to `{SITE_URL}/katalog` (filter query params NOT included in the canonical).
- **AC-7** Given a maker profile `/katalog/{slug}`, when its `<head>` is inspected, then it carries OG (`type=profile`, `url={SITE_URL}/katalog/{slug}`), Twitter summary, and canonical `{SITE_URL}/katalog/{slug}`. The OG title/description reuse the page's computed metadata (company name + bio-derived description).
- **AC-8** Given a product detail `/produkt/{productId}`, when its `<head>` is inspected, then it carries OG (`type=product`, `url={SITE_URL}/produkt/{productId}`), Twitter summary, and canonical `{SITE_URL}/produkt/{productId}`.
- **AC-9** Given a maker/product slug that 404s, when `generateMetadata` runs the NotFound fallback, then it still returns a valid `Metadata` (NotFound-safe title branch preserved) including a canonical for the requested URL — it does NOT throw and does NOT tell the indexer the entity is gone on a transient backend error.

## Technical notes

### Why a dedicated `NEXT_PUBLIC_SITE_URL` (not reuse the API base)

Canonical URLs, OG `url`, Twitter cards, and the sitemap must point at the **user-facing site origin** (`makables.cz`), which is a different host from the **API** (`NEXT_PUBLIC_API_PUBLIC_BASE_URL`, e.g. the Public API host / `localhost:5104` in dev). Conflating them would emit a canonical that points at the backend — a search engine would index (or try to) the API host. One small `site-url.ts` helper keeps every absolute URL in the SEO surface consistent and pointed at the right origin, exactly like `buildProductImageUrl` centralises the image-host base in `catalog.ts`.

### Why the dynamic-enumeration decision is left to the implementer (A.4)

Maker enumeration is cheap-ish — one paged walk of `getPagedMakers` (which already exists, is anonymous, and returns slugs), capped at a sane page count. Product-id enumeration is the problem: there is **no bulk product-id read** (the only product read is `getProductById(id)`, which needs an id you don't have yet; products are only reachable through a maker's profile). Enumerating every product would mean walking every maker, then every maker's product list — N+1 catalog reads at sitemap-generation time. That's disproportionate for an MVP frontend polish ticket, so product-id enumeration is **deferred** (flagged), maker enumeration is the default dynamic step, and a fully-static sitemap is an acceptable fallback if even the maker walk is judged too heavy. The implementer states which path was taken in the PR. The clean post-MVP fix is a backend bulk-slug/id feed (Option E), out of scope here.

### Why canonical excludes filter query params

The catalog page is `force-dynamic` and reads filters from the query string (`?category=&city=&minRating=&page=`). Every filter combination is a distinct URL. If each emitted its own canonical, Google would see hundreds of near-duplicate `/katalog?...` pages and split link equity across them. Pointing every filtered view's canonical at the bare `/katalog` consolidates all of them onto one indexable page — standard duplicate-content hygiene for faceted listings.

### Why `metadataBase` on the root layout

Next.js resolves relative `openGraph.url` / canonical values against `metadataBase`. With no `metadataBase` set, Next emits a build warning and resolves them against `http://localhost:3000`, producing wrong absolute URLs in production OG/canonical tags. Setting `metadataBase: new URL(SITE_URL)` once on the root layout fixes resolution for every descendant page; per-page `generateMetadata` can then emit either absolute (via `canonicalUrl`) or relative URLs and both resolve correctly.

### Why text-only OG (summary card) at MVP

OpenGraph + Twitter render a perfectly valid card from title + description + url alone (`twitter:card=summary` is the text-card variant). No brand 1200×630 image asset exists yet in `frontend/public/`. Inventing or stubbing one would ship a broken or off-brand share preview. The upgrade to `summary_large_image` is a single change in `site-url.ts` (add a default OG image) once the asset is designed — tracked in the launch checklist, not blocking the SEO wiring.

### Why robots allow-all (no Disallow on dashboards)

`robots.txt` is advisory, not a security boundary — a hostile crawler ignores it. The authenticated dashboards (`(customer)`, `(maker)`, `(admin)`) are protected by JWT auth (a crawler gets 401, never content) and are not in the sitemap, so they won't be discovered through it. Adding `Disallow: /admin` would *advertise* the admin path to anyone reading `robots.txt`. Allow-all is the correct MVP posture: index everything public, protect everything private with auth.
