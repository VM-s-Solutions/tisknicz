# T-0118c — Admin ops + control-plane UI (outbox / country-config / payout / GDPR delete-user)

## Context

T-0118c is the **third and final slice of the admin frontend** and the **highest-risk frontend ticket in the backlog** — it builds the operator's control-plane surfaces, including the **GDPR delete-user screen**, the only frontend that drives an irreversible hard-delete of user data. Per the 2026-06-15 split deliberation, T-0118 is sliced into three tickets shipping across **two PRs**: **T-0118a** (shell + dedicated admin login + read lists + overview KPIs) alone in **PR 1**; then **T-0118b** (order actions — refund / manual-state-change / dispute-resolve) **bundled with T-0118c** in **PR 2**, implemented **risk-ascending b → c** (the order actions land first, the control-plane + hard-delete land last). T-0118a is the **verification harness**: every effect this slice triggers (a requeued outbox row, an updated country config, a completed payout batch, an erased user) is asserted against the read lists a built, so a's surfaces must exist before b/c assert their effects.

This slice consumes four already-shipped admin backend commands, each behind an endpoint that is **already in the regenerated admin client** (`frontend/src/lib/api-client/admin-api.v1.ts`): **T-0109** outbox `POST /outbox-events/{id}/retry` + `/acknowledge`; **T-0108** country-config `PUT /country-configurations/{countryCode}`; **T-0103** payout `POST /payout-batches/{id}/complete` + the operator CSV `GET /payout-batches/{id}/csv`; **T-0110** GDPR `POST /users/{id}/erase`. The admin NSwag client was regenerated by those backend tickets (T-0105/0108/0109/0111 + T-0103/0110) — **this slice is a READ-ONLY consumer of the contract and performs NO regen** (a regen here would be blocked by the pre-commit hook anyway, ADR 0022).

Every surface mirrors the mutation semantics the backend locked, so the UI never invents a rule: the **outbox retry/ack** asymmetry (retry-on-processed is a hard 409 `outbox.alreadyProcessed`, re-acknowledge is benign — T-0109); the **country-config provider-change retype gate** (`country.providerConfirmationMismatch`) and unregistered-code rejection (`country.providerNotRegistered`) with the in-flight advisory count (T-0108); the **payout completion** capture of `BankReference` + optional `PaymentDate` and the forward-only terminal state (T-0103); and — the load-bearing one — the **delete-user double interlock**: type-to-confirm the user's exact email (`user.deleteConfirmationMismatch`) **plus** the in-flight-order block (`user.cannotDeleteWithInFlightOrders` when any order is in `PendingPayment / Paid / Accepted / Shipped`), with a re-call after a successful erase surfacing `user.notFound` as "already deleted" (T-0110 — NO Silent-Success on re-call). The UI adds friction and surfaces backend verdicts; it makes no money math, runs no state machine, and holds no business rule.

This slice is `security_touching: true` because the delete-user screen is the most destructive UI the platform will ever ship and the country-config form mutates the per-country control plane (ADR 0004) that drives VAT, fees, and provider selection for every subsequent order. The PR therefore requires **§secops Gate 3 review AND architect sign-off** (it carries T-0110's control-plane + the only hard-delete affordance).

**Dependency-gap fix (flag in the grooming commit):** T-0118's INDEX `depends_on` lists `T-0102, T-0105, T-0106, T-0107, T-0108, T-0109, T-0111` but **OMITS T-0110 and T-0103**, both of which this slice directly consumes (the erase endpoint is T-0110; the payout complete + CSV endpoints are T-0103). T-0118c's `depends_on` adds **T-0110** and **T-0103** (alongside T-0118a, T-0108, T-0109, T-0102); the overall T-0118 split inherits them. The PM updates the INDEX row in the grooming commit.

## Locked design decisions

Captured per `docs/process/deliberation.md`. The user locked the slice boundaries + the control-plane interaction shapes at the 2026-06-15 deliberation; the backend command semantics are ADR/ticket-locked (T-0108/0109/0103/0110) and consumed verbatim. PM-absorbed defaults follow the T-0080 / T-0087a / T-0116 admin-and-maker frontend precedents.

### A. User-locked at the 2026-06-15 deliberation (non-negotiable)

1. **Type-to-confirm is RESERVED exclusively for the delete-user screen.** The GDPR erase form requires the admin to **retype the user's exact email** into a confirmation field; a non-match disables the destructive button and, if the backend is reached, surfaces `user.deleteConfirmationMismatch`. No other surface in the admin frontend uses type-to-confirm — refunds and state changes use a modal (T-0118b), the country provider-change uses a **retype of the new provider code** (a distinct, lower-blast-radius interlock, T-0108), payout completion uses a modal. Type-the-email is the single strongest friction, reserved for the single irreversible action. **Rejected:** a plain "Are you sure?" confirm on delete (too weak for the only irreversible op — T-0110 Option G); spreading type-to-confirm to refunds/state-changes (friction inflation that trains the operator to type past every gate, devaluing the one place it must mean something).

2. **The delete-user screen surfaces BOTH gates the backend enforces, before the call.** (a) An **irreversibility banner** stating "hard delete, not recoverable; invoices retained per GDPR Art. 17(3)(b)" is prominent and always visible on the screen. (b) The **in-flight-order block** is surfaced proactively: when the user has any order in `PendingPayment / Paid / Accepted / Shipped`, the destructive button is **disabled** with the `user.cannotDeleteWithInFlightOrders` reason shown inline ("resolve in-flight orders first") — the admin sees WHY before clicking, not as a post-submit 409. The backend remains authoritative (the interlock is a server gate per T-0110 AC-7); the UI mirrors it for clarity. **Rejected:** surface the block only as a post-submit error (the admin types the email, clicks delete, then learns it was never going to work — wastes the most dangerous interaction on a preventable failure); hide the banner behind a tooltip (the irreversibility + the GDPR-retention fact must be unmissable on the screen).

3. **Payout management = VIEW + complete-action + CSV download; NO manual create-batch.** The payout surface shows batch status (list + the settlement facts), a **mark-completed** action capturing `BankReference` + optional `PaymentDate` (T-0103), and a **CSV download** (the operator bank file). Manual batch creation is **deferred to the T-0104 weekly timer + its HTTP escape-hatch** — the admin does not create batches from this UI. **Rejected:** a "create batch now" button here (the timer owns creation; an ad-hoc create button duplicates the T-0104 trigger and tempts double-runs — the escape-hatch is the HTTP-key path, not a UI affordance); hiding the CSV (the operator NEEDS the bank file to execute the wire — see B/§operator-CSV).

4. **Payout CSV is operator-only and the admin MAY download it here — inverting the maker-side absence (T-0116).** The CSV is the cross-maker bank file (every maker's account number + amount in one document). T-0116 forbids it on the maker surface (cross-maker PII). On the **admin** surface the operator is exactly the human who runs the wire, so the admin download is correct and expected. The download goes through `apiFetch` `parse: 'blob'` (never the NSwag `Promise<void>` file method, which discards the body — `csv()` at `admin-api.v1.ts:1109` does `response.text()` → `return;`). **Rejected:** reusing the maker CSV-exclusion posture on the admin surface (the admin IS the operator — the exclusion's rationale does not apply); a plain `<a href>` to `/csv` (would not carry the audience-cookie + RFC7807 discipline the runtime fetch layer manages — same reason `downloadFeeInvoice` is a blob helper).

5. **Provider-change confirmation = retype the new provider code in a confirmation modal (T-0108, US-admin-0006 AC-3).** When the country-config form changes any `Default*Provider` field, saving opens a **confirmation modal** that requires retyping the **new** provider code; a mismatch surfaces `country.providerConfirmationMismatch`. A VAT/fee-only edit saves without the modal (no provider field changed → no gate). The retype-the-provider-code idiom is distinct from the delete-user retype-the-email (A.1) — same friction family, different field, lower blast radius. **Rejected:** a boolean "confirm provider change" checkbox (one mis-click confirms — T-0108 Option A); blocking the save when in-flight orders exist (T-0108 WARNs with the advisory count — those orders keep their cached provider ref).

### B. ADR + pattern-locked (no relitigation)

- **patterns §B.1 / §B.14 + ADR 0024 — Server Components by default + SSR auth-cookie forwarding.** Every `page.tsx` is a Server Component with `dynamic = 'force-dynamic'`; reads forward the **admin-audience** cookie to the admin host. A customer/maker JWT replayed against the admin host 401s at the backend (ADR 0013); the frontend adds no parallel auth. Interactivity (the retry/ack buttons, the country-config form + provider modal, the complete-batch modal, the CSV download, the delete-user form) lives in isolated `'use client'` islands.
- **ADR 0013 — admin host audience.** All surfaces sit under the `(admin)` route group built by T-0118a (the shell + the dedicated `/admin/login` that posts `login('admin', ...)`). T-0118c adds routes within that shell; it does not build the login or the shell chrome (those are a).
- **patterns §B.4 + §B.16 — all data + mutations via `apiFetch` + a hand-written helper returning `Result<T, ApiError>`.** New `lib/api-client-helpers/admin-ops-client.ts` wraps the generated admin endpoints (retry, acknowledge, getCountryConfig, updateCountryConfig, listPayoutBatches, completePayoutBatch, downloadPayoutCsv, getUserForErase, eraseUser). No raw `fetch`, no `useEffect` data fetching. Mutations are called in event handlers (patterns §B.2).
- **ADR 0022 — NSwag is the contract; READ-ONLY consumer, NO regen.** The admin client was regenerated by the backend tickets (T-0108/0109/0103/0110). T-0118c consumes the already-regenerated types (`UpdateCountryConfigurationResponse`, `RetryOutboxEventResponse`, `AcknowledgeOutboxEventResponse`, `MarkPayoutBatchCompletedResponse`, `DeleteUserPermanentlyResponse`, `EraseUserRequest`). **No backend change, no regen** in this slice.
- **patterns §B.10 — `formatCzk(amountMinor, currency)`** for every money figure (payout batch totals, country-config `DefaultShippingPriceMinor`). VAT/fee basis points display via a keyed bp-to-percent presentation helper (no math beyond `/100` formatting — presentation, not a pricing rule).
- **patterns §B.5 + §B.18 — Czech-only UI via i18n keys; admin tone = vykání.** Zero hardcoded Czech outside `cs-CZ.ts`. New keys under `dashboard.admin.ops.*`. **The T8 consistency gate is LIVE** — a missing `cs-CZ` key for any admin UI string fails CI; every string this slice renders (including the irreversibility banner, the in-flight reason, every error code) gets a key. Admin tone is **vykání** (PM-absorbed; the admin audience is the operator, V-form).
- **patterns §B.8 — URL-state pagination via `searchParams` + `<Link>`** on the payout batch list (T-0087a / T-0116 precedent — `?page=` clamped ≥ 1, `page=1` dropped from canonical URLs).
- **blob-download discipline (T-0116 / T-0087b)** — the payout CSV download is `apiFetch` `parse: 'blob'` + `triggerBlobDownload` (programmatic anchor named `vyplaty-{batchNumber}.csv`), **never** the generated `csv()` method (NSwag `Promise<void>` file gap — it discards the body).
- **No business logic client-side.** State→label maps (outbox status, batch state, order state), bp→percent display, and "any in-flight order ⇒ disable delete" are presentation conditions over backend-supplied data; the authoritative gate is the server (T-0110 AC-7 / T-0108 AC-3). The frontend never decides whether an erase is allowed — it shows the backend's verdict and pre-disables the obvious blocked case.

### C. PM-absorbed (no user input needed)

- **`(admin)/layout.tsx` is the Phase-1 skeleton** (`return <>{children}</>` — verified). **T-0118a builds the real shell** (nav + admin chrome). T-0118c assumes a's shell exists and adds nav entries for its routes (Outbox, Country config link reachable from the overview/settings area, Výplaty, Uživatelé); if a's nav contract differs at impl time, the routes ship reachable by URL and the nav additions follow a's pattern. No layout rebuild here.
- **Outbox triage list (`/dashboard/admin/outbox`).** The stalled-event list is a **read** owned by the overview/T-0111 reads (the overview KPI "stalled-outbox count" deep-links here per T-0118a). If a dedicated stalled-list endpoint is not yet exposed, **log a thin follow-up** (do NOT add backend in this frontend bundle — same posture as the T-0118a KPI count-endpoint follow-ups) and render from whatever read a surfaces. The two **actions** (retry, acknowledge) are the T-0109 endpoints this slice owns.
- **Retry is a one-shot nudge, no reason; Acknowledge requires a reason (≤2000 chars).** Mirrors T-0109: the retry button is a direct action (optionally a light confirm); the acknowledge action opens a small inline form capturing the mandatory reason (the "give up, stop bothering me" note that rides the audit log). Retry-on-processed surfaces the `outbox.alreadyProcessed` 409 as a clear "already ran — nothing to retry" alert (NOT a silent success); re-acknowledge is benign (200).
- **Country-config form (`/dashboard/admin/countries/{code}`)** edits exactly the T-0108 editable set: `StandardVatRateBp`, `ReducedVatRateBp`, `InvoicingMode`, `PlatformFeeRateBp`, `DefaultShippingPriceMinor`, and the four `Default*Provider` codes — plus a mandatory `Reason`. The form is a client island; the GET pre-fills from the current row. On a provider change → the **retype-new-provider-code confirmation modal** (A.5). The response's `inFlightOrderCount` advisory is surfaced after a provider-change save ("N rozpracovaných objednávek si ponechá stávajícího poskytovatele") — informational, never blocking.
- **Payout view (`/dashboard/admin/vyplaty`)** is a paginated batch list (batch number, total, maker/order count, state badge — `Processing → "Zpracovává se"`, `Completed → "Vyplaceno"` — settlement date/`BankReference` when present) + per-row **CSV download** + a **mark-completed modal** for `Processing` batches. The complete modal captures `BankReference` (required) + `PaymentDate` (optional date picker) per T-0103; the button is disabled-while-pending (idempotency lock — a double-submit re-call is a backend Silent-Success, but the UI does not invite it). Completed batches show no complete action (forward-only terminal state).
- **Delete-user surface (`/dashboard/admin/users` or inline on a user detail).** A user lookup/detail renders: the **irreversibility banner** (A.2a, always visible), the user's email + in-flight-order summary, the **type-the-exact-email** confirmation field (A.1) that gates the destructive button (disabled until the typed value matches the displayed email), a mandatory `Reason` (≤2000 chars, GDPR ticket ref), and the **in-flight block** (A.2b — button disabled + `user.cannotDeleteWithInFlightOrders` reason when any in-flight order). A successful erase confirms and removes the user from a's read list; a re-call surfaces `user.notFound` rendered as "uživatel již byl smazán" (already deleted — NOT a silent success, per T-0110's no-Silent-Success rule).
- **Idempotency / double-submit locks** on every mutation button (retry, acknowledge, complete-batch, update-config, erase) — disabled-while-pending (T-0087b precedent). The erase button additionally requires the email match AND no in-flight orders AND a non-empty reason before it is ever enabled.
- **Loading + error route segments** mirror the T-0087a/T-0116 skeletons (`loading.tsx` pulse, `error.tsx` last-resort boundary) for each route folder.
- **Every backend error code rendered via its `cs-CZ` key** (T8 gate): `outbox.rowNotFound`, `outbox.alreadyProcessed`, `country.providerNotRegistered`, `country.providerConfirmationMismatch`, `countryConfiguration.notFound`, `payoutBatch.notFound`, `payoutBatch.notProcessing`, `user.notFound`, `user.deleteConfirmationMismatch`, `user.cannotDeleteWithInFlightOrders` — most already keyed by their backend tickets (T-0108/0109/0103/0110); this slice adds any missing parity key + the `dashboard.admin.ops.*` UI strings.

## Scope (risk-ascending within the slice)

### (1) Outbox retry / acknowledge — `/dashboard/admin/outbox`

- **`(admin)/dashboard/admin/outbox/page.tsx`** — Server Component, `force-dynamic`. Renders the stalled-event list (from the a/T-0111 read; thin follow-up logged if no dedicated endpoint) — per row: event type, aggregate id, `RetryCount`, `LastErrorKind`/`LastErrorCode`, `NextRetryAt`/stalled marker — with **Retry** and **Acknowledge** actions.
- **`outbox-actions.tsx`** — `'use client'` island: `retryOutboxEvent(id)` (one-shot, optional light confirm; `outbox.alreadyProcessed` 409 → clear alert) + `acknowledgeOutboxEvent(id, reason)` (inline reason form, mandatory ≤2000). Disabled-while-pending; inline i18n-keyed result/error.

### (2) Country-config edit — `/dashboard/admin/countries/{code}`

- **`(admin)/dashboard/admin/countries/[code]/page.tsx`** — Server Component, `force-dynamic`. GETs the current `CountryConfiguration` (pre-fill); `notFound()` on `countryConfiguration.notFound`.
- **`country-config-form.tsx`** — `'use client'` island: the editable T-0108 field set + mandatory `Reason`. On submit, if any `Default*Provider` changed → open the **provider-change confirmation modal** (retype the new provider code; `country.providerConfirmationMismatch` on mismatch); a VAT/fee-only edit saves directly. Surfaces `country.providerNotRegistered` on an unregistered code and the `inFlightOrderCount` advisory after a provider-change save. Disabled-while-pending.

### (3) Payout view + complete + CSV — `/dashboard/admin/vyplaty`

- **`(admin)/dashboard/admin/vyplaty/page.tsx`** — Server Component, `force-dynamic`, URL-state `?page=`. Paginated batch list (number, total via `formatCzk`, maker/order count, state badge, settlement date + `BankReference` when `Completed`). Per `Processing` row: **mark-completed** trigger. Per row: **CSV download**.
- **`payout-row.tsx`** — server-rendered row/card (mobile cards `< md`, grid `≥ md`), state badge mapping (`Processing`/`Completed`).
- **`complete-batch-modal.tsx`** — `'use client'` island: `BankReference` (required) + `PaymentDate` (optional) modal → `completePayoutBatch(id, { bankReference, paymentDate })`; disabled-while-pending idempotency lock. Surfaces `payoutBatch.notProcessing` / re-completion (`AlreadyCompleted`) coherently.
- **`payout-csv-download.tsx`** — `'use client'` island: blob fetch via `apiFetch` `parse: 'blob'` + `triggerBlobDownload` named `vyplaty-{batchNumber}.csv`. **Admin/operator-only download** (A.4 — inverts the T-0116 maker absence). Inline error alert.

### (4) Delete-user — `/dashboard/admin/users` (THE DANGEROUS SCREEN)

- **`(admin)/dashboard/admin/users/page.tsx`** (or an inline panel on a user detail) — Server Component, `force-dynamic`. Resolves the target user (email + in-flight-order summary) from the a/T-0111 read.
- **`delete-user-panel.tsx`** — `'use client'` island, the most carefully-built component in the slice:
  - **Irreversibility banner** (A.2a) — prominent, always visible: "Nevratné smazání — data uživatele nelze obnovit. Faktury zůstávají zachovány dle GDPR čl. 17 odst. 3 písm. b)."
  - **Type-the-exact-email** confirmation field (A.1) — the destructive button stays disabled until the typed value matches the displayed user email (mirrors `user.deleteConfirmationMismatch`).
  - **In-flight block** (A.2b) — when any order is in `PendingPayment / Paid / Accepted / Shipped`, the button is disabled with the `user.cannotDeleteWithInFlightOrders` reason inline ("nejprve vyřešte rozpracované objednávky").
  - **Mandatory `Reason`** (≤2000, GDPR ticket ref).
  - **Erase action** → `eraseUser(id, { confirmedEmail, reason })`; disabled-while-pending. On success: confirm + remove from a's read list. On re-call / already gone: `user.notFound` rendered as "uživatel již byl smazán" (NOT a silent success).
- The button enable predicate is purely presentational (email-match AND no-in-flight AND non-empty-reason); the **server is authoritative** (T-0110 enforces both gates regardless of the UI).

## Alternatives Considered

- **Option A — Surface the in-flight-order block only as a post-submit 409 on the delete-user screen.** *Rejected per A.2b* — the most dangerous interaction in the product would be spent on a preventable failure: the admin reads the banner, types the exact email, clicks delete, and only then learns it was never going to work. Pre-disabling the button with the inline `user.cannotDeleteWithInFlightOrders` reason tells the admin WHY up front; the server gate (T-0110 AC-7) stays authoritative.
- **Option B — A plain "Are you sure?" confirm dialog for the erase (no email retype).** *Rejected per A.1 / T-0110 Option G* — a single click is too weak for the only irreversible action in the system. Retyping the exact user email forces the admin to confirm they have the right person and mirrors `user.deleteConfirmationMismatch`. Type-to-confirm is reserved for exactly this screen.
- **Option C — Spread type-to-confirm to refunds and manual state changes.** *Rejected per A.1* — refunds (T-0118b) move money but are recoverable/forward-correctable; a modal + disabled-while-pending is sufficient. Inflating type-to-confirm to every gate trains the operator to type past it reflexively, devaluing the one place it must carry weight. Type-the-email stays exclusive to delete-user.
- **Option D — A "create payout batch now" button on the admin payout view.** *Rejected per A.3* — batch creation is owned by the T-0104 weekly timer (and its HTTP escape-hatch for manual runs). A UI create button duplicates that trigger and tempts double-runs; the admin payout surface is VIEW + complete + CSV only.
- **Option E — Hide / omit the payout CSV on the admin surface (mirror the T-0116 maker exclusion).** *Rejected per A.4* — the maker exclusion exists because the CSV is cross-maker PII a maker must never see. The admin IS the operator who runs the bank wire; the CSV is precisely their tool. The exclusion's rationale does not transfer; the admin download is correct and expected (it inverts the maker absence).
- **Option F — Use the generated `csv()` client method for the CSV download.** *Rejected per A.4 / B* — NSwag types the file response as `Promise<void>` and discards the body (`admin-api.v1.ts:1109` does `response.text()` → `return;`). The blob helper through `apiFetch` (`parse: 'blob'`) is the only path that preserves the body, the audience cookie, the timeout, and RFC7807 parsing — the same reason the maker fee-invoice download is hand-written (T-0116 Option F).
- **Option G — A boolean "I confirm the provider change" checkbox instead of retyping the new provider code.** *Rejected per A.5 / T-0108 Option A* — a checkbox is one mis-click from confirming a catastrophic provider swap. Retyping the new code forces the admin to physically re-enter the exact value; a typo fails the gate (`country.providerConfirmationMismatch`) instead of committing a wrong provider for every future order in the country.
- **Option H — Block the country-config save while in-flight orders exist.** *Rejected per A.5 / T-0108 Q-C* — in-flight orders keep their cached `PaymentProviderRef`; switching the default only affects NEW orders. Blocking would strand the admin behind unrelated orders. The UI WARNs with the `inFlightOrderCount` advisory after a provider-change save; it never blocks.
- **Option I — Silent-success the erase re-call (show "deleted" again if the user is already gone).** *Rejected per T-0110 Option E* — erasure is not idempotent: the row is gone, so a re-call has nothing to act on. The honest answer is `user.notFound`, which the UI renders as "uživatel již byl smazán" — surfacing a double-click as a clear "already gone" rather than falsely claiming a second erasure.
- **Option J — Fold all four ops surfaces into one mega control-plane page.** *Rejected* — outbox triage, country config, payout settlement, and GDPR erase have different shapes, different risk profiles, and different routes; one page would couple the lowest-risk action (retry) to the highest (erase) and complicate the per-route loading/error/SSR discipline. Four routes, shared conventions, isolated blast radius (T-0087a Option G precedent).

## Out of scope

- **T-0118a (shell + dedicated `/admin/login` + read lists + overview KPIs).** The verification harness; ships in PR 1. T-0118c assumes its shell + reads exist.
- **T-0118b (order actions: refund modal + manual-state-change modal + dispute-resolve inline form).** The sibling slice in PR 2; lands first (risk-ascending b → c). T-0118c does not build the order action surfaces.
- **All backend commands** — T-0109 (outbox retry/ack), T-0108 (country-config update + `IProviderRegistry`), T-0103 (payout complete + `BankReference` + CSV), T-0110 (GDPR erase + the `IUserDataDeletionService` matrix). Upstream; consumed here. **No NSwag regen** in this slice.
- **Manual payout-batch creation** — deferred to the T-0104 weekly timer + its HTTP escape-hatch (A.3). Not a UI affordance here.

## Technical notes

### Why the delete-user screen surfaces both gates before the call

T-0110 enforces two server gates: the email-retype (`user.deleteConfirmationMismatch`) and the in-flight-order interlock (`user.cannotDeleteWithInFlightOrders`). The UI mirrors both *proactively* — the destructive button is disabled until the typed email matches AND no order is in-flight AND a reason is present — so the admin sees exactly why a deletion is or isn't possible before spending the most dangerous interaction in the product. The server remains the authority (the UI predicate is presentational; T-0110 re-checks regardless), but a control-plane UI that lets the operator click "delete" only to bounce off a 409 wastes the one click that must never be wasted.

### Why type-to-confirm is reserved for delete-user

Friction only works if it is rare. Type-the-exact-email is the strongest gate the admin UI offers; spending it on the single irreversible action (GDPR hard-delete) keeps it meaningful. Refunds and state changes (T-0118b) are recoverable/forward-correctable and use a modal; the country provider-change uses retype-the-provider-code (a related but lower-blast-radius interlock). If every gate demanded typing, the operator would type past them reflexively and the delete-user retype would lose its signal.

### Why the admin CSV inverts the maker absence

T-0116 forbids the payout CSV on the maker surface because it is the cross-maker bank file (every maker's account number in one document) — a GDPR + competitive-data leak if a maker sees it. The admin is the operator who actually runs the bank wire; the CSV is their working tool. The exclusion's rationale is audience-specific, so it inverts cleanly: forbidden for makers, expected for the admin/operator. The download still goes through the blob helper (`apiFetch` `parse: 'blob'`), never the generated `Promise<void>` file method that discards the body.

### Why no regen and no backend in this slice

The admin endpoints this slice drives were all regenerated into `admin-api.v1.ts` by their backend tickets (T-0108/0109/0103/0110/0111). T-0118c is a pure presentation consumer: it calls those typed methods (or, for the CSV blob, hand-rolls the fetch the NSwag file gap forces) and renders the results. Any contract change would belong to the backend ticket, not here; the pre-commit hook blocks manual `api-client/` edits regardless.

## Risk / mitigation

- **An accidental hard-delete (the irreversible op, fronted by a UI).** *Mitigation:* the double interlock surfaced before the call (type-the-email + in-flight block), the always-visible irreversibility banner, disabled-while-pending, the server as the final authority (T-0110), AND **§secops Gate 3 + architect sign-off on the PR**. The button is enabled only when email-match AND no-in-flight AND reason-present all hold.
- **Type-to-confirm leaks to other gates.** *Mitigation:* A.1 lock + AC-15 grep-for-exclusivity (type-to-confirm appears only in `delete-user-panel.tsx`); refunds/state-changes (T-0118b) use modals, provider-change uses retype-the-code.
- **CSV downloaded via the generated `Promise<void>` method (body discarded).** *Mitigation:* B lock + Option F rebuttal + AC-9 names the blob helper; `downloadPayoutCsv` is the only CSV path and it uses `parse: 'blob'`.
- **Provider-change committed by a mis-click.** *Mitigation:* A.5 retype-the-new-code modal + `country.providerConfirmationMismatch` surfacing; no boolean confirm anywhere.
- **Stalled-outbox list endpoint not yet exposed.** *Mitigation:* render from a's reads; log a thin follow-up; do NOT add backend in this frontend bundle.
- **Dependency-gap (T-0110 + T-0103 missing from T-0118's INDEX `depends_on`).** *Mitigation:* added to T-0118c's `depends_on` + flagged in the grooming commit; PM updates the INDEX row.
- **Admin NSwag drift (consuming a stale contract).** *Mitigation:* read-only consumer of the client the backend tickets regenerated; CI contract-parity check (ADR 0022) catches drift; no regen attempted here.
