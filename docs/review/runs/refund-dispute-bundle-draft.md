## Bundle scope (T-0105 + T-0106 + T-0107)

Three backend-led tickets completing the order-exception lane: money out (refund), lifecycle suspension (dispute parenthesis state), and the admin escape hatch (strict-allow-list manual transition). The interlock is load-bearing and locked: T-0106's `ResolveDispute(Refunded)` dispatches `RefundOrder.Command` in-process (nested MediatR), and T-0107's policy names `RefundOrder`/`OpenDispute`/`ResolveDispute` as the only sanctioned paths into/out of `Refunded`/`Disputed` — so implementation order T-0105 → T-0106 → T-0107 must not be reshuffled.

## Pre-flight risks (HIGH first)

### HIGH

- **HIGH-1: Provider-first refund ordering (locked A.5) — verify the asymmetry is implemented the right way round.** The failure modes are NOT symmetric and the ticket's reasoning must hold in the code:
  - *Refunded-but-unrecorded* (provider success → mutation/commit failure): recoverable. For a **full** refund the admin retry is gateway-safe (Comgate caps cumulative refunds at the capture). For a **partial** refund the gateway cap does NOT make retry intent-safe — a retried 400 Kč partial re-issues 400 Kč (cumulative 800 ≤ capture, gateway accepts). This is accepted per Risk + Alternatives G (no idempotency key, T-0118 confirm UI bounds it) — but it makes the **step-6 Critical log content load-bearing**: it must carry `OrderId` + `PaymentProviderRef` + `AmountMinor` so ops can reconcile against the Comgate portal. A bare "refund record failed" Critical is a request-changes.
  - *Recorded-but-not-refunded* (mutate first, provider fails): NOT recoverable — no compensation API exists. **Hard-block any inversion**: the handler sequence must be session-check → load → silent-success gate → `noProviderRef` + `ValidateRefund` pre-flight → **`RefundAsync` (money moves)** → `order.Refund` mutation → email enqueue. Zero entity mutation may precede the provider call (AC-5's "order row byte-identical" depends on it — verify nothing stamps `UpdatedAt` or anything else pre-provider).
  - Pre-flight uses the SAME predicate the mutator calls (`Order.Refund` must internally call `ValidateRefund`, not duplicate its checks — one source of truth, no drift). Provider failure → error surfaced verbatim, no outbox, no audit row (UoW + audit behaviors skip on failure — automatic, but integration test AC-5 must assert all three).

- **HIGH-2: Partial-refund arithmetic — `long` minor units everywhere, cumulative invariant.** Verify: `RefundedAmountMinor += amountMinor` accumulation; `RemainingRefundableMinor => TotalAmountMinor - RefundedAmountMinor` (computed — must be **EF-ignored**, not mapped; watch OrderConfiguration); over-refund gate `amountMinor > RemainingRefundableMinor` → `amountExceedsRemaining` **before** the provider call (AC-3: provider never called); state flips ONLY at cumulative == total (`State = Refunded` + `RefundedAt`); partial leaves State + `RefundedAt` untouched. Post-condition invariant `RefundedAmountMinor <= TotalAmountMinor` is guaranteed by the predicate gate — domain test 1 (prior partial, then remaining+1) pins it. **No `decimal`/`double` anywhere** in the path including the Comgate adapter (`amount` form field from `long` via `ToString(CultureInfo.InvariantCulture)`, matching the `price` field precedent at `ComgatePaymentProvider.cs:112`). Migration: `refunded_amount_minor BIGINT NOT NULL DEFAULT 0` — money convention satisfied with the existing `currency CHAR(3)`; no new currency column (refunds always in `Order.Currency`).

- **HIGH-3: ResolveDispute → nested `mediator.Send(RefundOrder.Command)` — UoW boundary analysis (verified against the registered pipeline).** Because UoW wraps AdminAudit (`AddMakablesMediator.cs:44-46`), the nested dispatch behaves as follows — the implementer and the final review must verify each leg:
  1. **Inner success**: the inner RefundOrder's UoW `SaveChangesAsync` flushes the SHARED scoped DbContext — committing the outer resolution mutations (restore + `dispute.Resolve` + customer email outbox, all staged before the dispatch per §C.3) + refund mutation + refund outbox + **refund audit row** in ONE commit. Atomic, as the ticket claims. The OUTER `ResolveDispute` audit row is appended after and lands in a **second** commit (outer UoW) — a residual ADR 0014 deviation (the outer command's audit row is not atomic with its mutation). Acceptable; integration test AC-9 e2e should assert **both** audit rows exist.
  2. **Inner failure (e.g. Comgate Permanent)**: inner handler returns failure → inner audit + inner UoW both skip → outer handler MUST propagate the failure → outer UoW skips → the entire staged change-set (restore, dispute resolution, email) is discarded at scope end. Dispute stays OPEN (Risk 4 satisfied). **Request changes if the handler catches-and-continues or half-resolves.**
  3. **Hard-blocks**: dispatching via a fresh `IServiceScopeFactory` scope (breaks DbContext + session sharing — the fail-closed session check inside RefundOrder relies on the shared scoped `IUserSessionProvider`); calling the Comgate provider directly inside ResolveDispute (Option E rejected — duplicates the tested money path); wrapping the nested Send in a manual transaction.
  4. The inner `GetByIdUnscopedAsync` load resolves to the SAME tracked instance (identity map) → `ValidateRefund` evaluates against the **restored** (uncommitted) state — which is the whole point of restore-then-refund. The inner audit `before` snapshot also reads through the change tracker (`FindAsync` in `AdminAuditLogWriter.cs:75`) → shows the restored state, not `Disputed`. Correct semantics; tests should not "fix" this.
  5. **Unspecified by the ticket**: the nested Command's `Reason` (Validator requires NotEmpty ≤2000 — expect ResolutionNotes or a canned "dispute resolution T-0106" string) and `AcknowledgePostPayout` (restored state can never be `Completed` since Completed is not disputable per §C.1 → pass `false`; if legacy data ever produced a Completed restore, `postPayoutAckRequired` fails the resolve and the dispute stays open — correct fail-safe). Implementer documents the choice.
  6. **Double customer email on Refunded outcome** (`order.disputeResolved.customerEmail` + `order.refunded.customerEmail`) is BY DESIGN — final review must not flag it as a duplicate-send bug.

- **HIGH-4: T-0107 allow-list must not route around domain invariants — and `Order.Cancel`'s default parameter is live ammunition.** Verified on the tree: `Cancel(IClock clock, OrderCancellationSource source = OrderCancellationSource.Customer)` (`Order.cs:776-778`) — the default-parameter shape the order-cleanup draft warned against shipped anyway.
