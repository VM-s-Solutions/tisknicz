## Ticket interpretation

This is a pure-domain + database PR. It ships:

1. The `Invoice` aggregate (`Core.Domain/Invoices/Invoice.cs`) — sealed, `Auditable`, factory-only construction (`Issue(...)`), XOR aggregate-link invariant (OrderId vs PayoutBatchId), inline issuer + recipient snapshots, money breakdown per ADR 0003, set-once `AttachPdfBlobPath(string) → BusinessResult`. No state machine (Invoice is born complete; only the PDF-path attaches later).
2. `InvoiceType` enum and `IInvoiceRepository` (read-only surface — no `UpdateAsync`, no `DeleteAsync`; scoped per ADR 0013 with `ForCustomer`, `ForMaker`, `Unscoped`, plus typed `GetByInvoiceNumberAsync` / `GetByOrderIdAsync` for T-0068b idempotency).
3. The EF mapping (`InvoiceConfiguration`), the auto-generated `Invoices` migration, and DI wiring in `AddMakablesInfrastructure`.
4. The **TZ-aware-year migration of `IInvoiceNumberGenerator`** that ADR 0009's T-0062 amendment (lines 98–102) explicitly named T-0068 for. The new signature is `Task<string> NextAsync(string countryCode, CancellationToken ct)` — the `int year` parameter is removed. Zero callers exist yet, so this is a "free" interface change.
5. Race-safety + year-contract integration tests reusing `PostgresHarness` from T-0062, mirroring the `OrderNumberGeneratorRaceSafetyTests` + `OrderNumberGeneratorYearContractTests` shape 1:1.
6. Docs: amend `docs/adr/0009-numbering.md`, add implementation pointer to `docs/architecture/roles/invoice.md`, split T-0068 → T-0068a/b in `docs/tickets/INDEX.md`, rewire T-0069's `depends_on`.

The slice ends BEFORE QuestPDF, blob upload, `IInvoiceService.IssueAsync`, the `MarkOrderPaid` third outbox enqueue, and any controller. Those belong to T-0068b. There is no NSwag regen (no controllers ship). There is no l10n change (`InvoiceBlobPathAlreadySet` surfaces in admin/logs only at this stage per the locked decision).

- **A.7 Sync, stateless validation belongs upstream.** Not applicable at T-0068a (no `Features/Invoices/IssueInvoice.cs` here — that's T-0068b). Reviewer notes this so the PR description doesn't accidentally claim "Validator added".

## Pre-flight risks

These are the things most likely to go wrong on the diff. Each is a candidate hard-block at PR-open if not addressed; reviewer will verify resolution against the code.

1. **TZ-aware migration risk — "zero callers" claim.** The ticket asserts no callers exist for the old `IInvoiceNumberGenerator.NextAsync(string, int, CancellationToken)` signature. Reviewer will independently `grep` for `IInvoiceNumberGenerator` / `_invoiceNumbers.NextAsync` / `invoiceNumberGenerator.NextAsync` across the whole `backend/src/` tree at PR-open. Current grep at preliminary time confirms only 5 hits: the interface declaration, the impl, the DI registration in `AddMakablesInfrastructure.cs:135`, a `NumberingSequence.cs` XML-doc cross-reference, and a `WebHostStartupTests.cs:73` DI smoke-test that just calls `sp.GetService<IInvoiceNumberGenerator>()`. None pass `int year`. **Risk level: LOW.** If a sixth hit appears in the diff, reviewer will verify it migrates to the new signature.
2. **Partial unique index on `order_id` — soft-delete-vs-re-issue tension.** Ticket line 41 (absorbed decision) says `ix_invoices_order_id` partial unique `WHERE order_id IS NOT NULL AND is_active` keeps numbering gap-free under soft-delete-then-reissue (a soft-deleted invoice frees its order_id slot; the re-issued invoice gets a fresh number from the sequence). This is internally consistent BUT requires T-0068b's `IInvoiceService.IssueAsync` to call `GetByOrderIdAsync` BEFORE `IInvoiceNumberGenerator.NextAsync` — otherwise the gap-free invariant breaks (a number is consumed for an idempotent retry that then short-circuits). **Risk level: MEDIUM.** Reviewer will verify the XML doc on `GetByOrderIdAsync` explicitly calls out this ordering requirement so T-0068b's implementer doesn't get it wrong. If the XML doc is silent, request changes.
3. **`UniqueConstraintTranslator` mapping policy.** Per the file's "defence-in-depth invariants stay unmapped" rule at `UniqueConstraintTranslator.cs:67-82`, the new `ix_invoices_invoice_number` is gap-free-by-generator (just like `ix_orders_order_number`), so it SHOULD stay unmapped — a 23505 there means the generator was bypassed. Similarly `ix_invoices_order_id` is the idempotency guard for T-0068b: a 23505 there means the pre-check (`GetByOrderIdAsync`) missed and T-0068b should rethrow + let the next idempotent webhook retry succeed — same logic as `ix_orders_payment_provider_ref` at lines 73-81. **Risk level: MEDIUM.** If the diff adds entries for either index to `UniqueConstraintTranslator.Mappings`, reviewer will request changes per the file's commented-out unmapped policy.
4. **`PostgresHarness.ResetMutableTablesAsync` extension is idempotent.** The ticket §"Why PostgresHarness reuse" claims the TRUNCATE just needs `invoices` appended to the existing CASCADE list at `PostgresHarness.cs:116`. The CASCADE already trickles down from `users` / `orders` (parent of invoices via the order_id FK). However, since invoices have an FK to orders with `ON DELETE RESTRICT`, simply adding `invoices` to the explicit table list is necessary so the TRUNCATE order doesn't trip on the RESTRICT — Postgres TRUNCATE ... CASCADE handles this, but only because all named tables get the simultaneous truncation. **Risk level: LOW.** Verify the table list adds `invoices` to the explicit list (not relying solely on CASCADE from `orders`); the comment block at lines 106-114 grows by one line per the precedent.
5. **`payout_batch_id` column without FK ships now.** Ticket §"Why the payout_batch_id column ships here with no FK" explains the FK is deferred to T-0101. Reviewer will verify the column is `text` (nullable), the InvoiceConfiguration has `builder.Property(i => i.PayoutBatchId).HasColumnName("payout_batch_id").HasMaxLength(40)`, and a TODO/XML-doc comment cross-references T-0101. **Risk level: LOW.** If the column is forgotten OR the FK is added prematurely, request changes.
6. **InvoiceConfiguration must declare `HasConversion<string>()` for both enums.** `InvoiceType` and `InvoicingMode` both get string-storage per ticket scope ("InvoiceType + InvoicingMode as string via HasConversion"). Precedent: `OrderConfiguration.cs:61` (`ShippingMethod`) and `:70` (`State`). The string lengths matter — `OrderState` uses `HasMaxLength(20)`; `InvoiceType` and `InvoicingMode` values are short ("Customer", "Fee", "None", "StandardVat", "ReverseCharge", "StrictFiscalReporting"), so `HasMaxLength(40)` is comfortable. Reviewer will verify both columns use string storage so a `dotnet ef database update` produces a readable schema.
7. **§ 35 10-year retention TODO must be a code comment, not a `TODO` without owner.** CLAUDE.md hygiene rule: "no TODO without owner". The ticket §"Open decisions absorbed by PM" says comment-only TODO in `InvoiceConfiguration.cs` cross-referencing the Azure Blob lifecycle deploy ticket. Reviewer will verify the comment is shaped as `// § 35 retention: 10 years. Blob-lifecycle policy lives in deploy IaC (TBD ticket).` — i.e. anchored to a follow-up reference, not a bare `TODO`.
8. **Set-once idempotency semantic.** Ticket line 42 (absorbed decision): "idempotent same-value succeed, different-value fail". The reference precedent is `Order.MarkAsPaid`'s set-once on `PaymentProviderRef` at `Order.cs:488-493`: same value → continue; different non-null → `BusinessResult.Failure(...)`. Reviewer will verify `AttachPdfBlobPath` follows this exact shape: a second call with same value returns `BusinessResult.Success()` idempotently; different value returns `BusinessResult.Failure(Error.Conflict("pdfBlobPath", BusinessErrorMessage.InvoiceBlobPathAlreadySet))`. `string.IsNullOrWhiteSpace` for the incoming path → `throw new ArgumentException`. **AC-3 pins this verbatim.**
9. **DUZP `TaxableSupplyDate` is `DateOnly?` — not `DateTimeOffset?`.** Locked decision 3 says DUZP = `Order.PaidAt.DateOfDayInCountryTz(countryConfiguration.TimeZoneId)`. The column type is `DateOnly?` for non-VAT-payer mode. Reviewer will verify the EF column maps to Postgres `date` (not `timestamptz`) — Npgsql translates `DateOnly` to `date` natively.
10. **InvoiceTests count discipline.** Ticket §Tests promises ~12 InvoiceTests. Walking AC-1, AC-2, AC-3 alone yields: AmountBalance fail (AC-1), XOR both-set fail (AC-2), XOR both-null fail (AC-2), Currency length fail, blank issuer fail, blank recipient fail, None+nonzero-VAT fail, StandardVat happy path, None happy path, AttachPdfBlobPath happy path (AC-3), AttachPdfBlobPath idempotent same-value (AC-3), AttachPdfBlobPath set-once different-value (AC-3), AttachPdfBlobPath null/blank rejected. ## Open items the implementer should confirm

These are not blocking; the implementer should call them out in the PR description so reviewer doesn't have to ask:

1. **Does `InvoiceNumberGenerator` share `NumberingSequenceAllocator`'s transaction with the caller, or open its own?** Per `NumberingSequenceAllocator.AllocateAsync` XML doc (`NumberingSequenceAllocator.cs:36-40`), the lock requires the surrounding transaction. The impl MUST NOT call `BeginTransactionAsync` itself — it inherits the UoW. Reviewer will confirm this matches `OrderNumberGenerator.cs:49-50` (which delegates without opening a transaction).
2. **Is `PostgresHarness.ResetMutableTablesAsync` idempotent on a fresh schema where `invoices` table doesn't yet exist?** The TRUNCATE will fail on a missing table. Since the harness's `InitializeAsync` runs `MigrateAsync()` on startup (`PostgresHarness.cs:70-71`), the table exists by the time `Reset` is called in test ctors. Risk only manifests if a future migration drops the table; out of scope for this PR. Reviewer will note for future runs.
3. **Does `IInvoiceRepository.ForMaker(makerId)` join through `Order.MakerId`?** Customer invoices have `OrderId` but NOT `MakerId` (the maker is derivable through the order). The XML doc must explicitly say "joins via `Order.MakerId`" — a maker-side `IQueryable<Invoice>` returning `dbContext.Invoices.Where(i => i.MakerId == makerId)` would NOT compile (Invoice has no `MakerId`). Reviewer will verify the LINQ shape — likely `db.Set<Invoice>().Join(db.Set<Order>(), i => i.OrderId, o => o.Id, (i, o) => new { i, o }).Where(x => x.o.MakerId == makerId).Select(x => x.i)` or equivalent. Fee-side join (via `PayoutBatch.MakerId`) is the deferred-to-T-0101 TODO.
4. **Does the `OrderId` FK constraint name follow the EF convention?** Reviewer will verify the migration emits `FK_invoices_orders_OrderId` (or snake-cased per house convention — house style seems mixed; the `ix_*` indexes are snake_case but EF auto-generates PascalCase FK names by default). Either is acceptable as long as the existing precedent is followed.
5. **Is the `payout_batch_id` column included in `ix_invoices_order_id`'s `IS NOT NULL` filter logic?** Specifically: should the partial unique on order_id be `WHERE order_id IS NOT NULL AND is_active` (as ticket line 61 says) OR `WHERE order_id IS NOT NULL AND payout_batch_id IS NULL AND is_active` (to defensively assert XOR)? Reviewer leans toward the simpler ticket-stated form because the XOR is already enforced by the factory at the application layer; the partial index is just guarding the customer-invoice happy path. Implementer to confirm in PR description.
