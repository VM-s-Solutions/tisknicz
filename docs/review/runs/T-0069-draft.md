# T-0069 — Reviewer preliminary verdict (draft)

> Written in parallel with the dotnet-backend implementer per the parallel-reviewer rule (`docs/process/routing.md`). This is NOT the final verdict; it is the reviewer's structural read of the ticket + ADRs + precedents BEFORE the diff lands. The verdict at PR-open re-walks the diff against this baseline.

## Ticket interpretation

T-0069 closes the Phase 4 invoice loop by wiring the queue-trigger that dispatches `IssueInvoice.Command` (the third atomic outbox event enqueued by `MarkOrderPaid.Handler` per T-0068b) and extending the existing customer order-paid email path to attach the rendered PDF.

The PR's center of gravity is **four extension seams**: (1) a new `GenerateInvoiceFunction` mirroring T-0029's `SendEmailFunction` shape (thin MediatR wrapper); (2) `OutboxDispatcher.DispatchDueAsync` gains a second routing branch keyed off `OutboxEventTypes.IsInvoiceGenerate(...)`; (3) `EmailSendService.SendOrderPaidCustomerEmailAsync` is extended to lookup the Invoice by OrderId at send-time, download the PDF, and pass an `Attachment` on `EmailMessage`; (4) `SendGridEmailProvider.SendAsync` wires `sgMessage.AddAttachment(...)` when non-null. Race tolerance is via the existing outbox retry policy (Transient `InvoiceNotYetRendered` → 1m retry).

No public contract changes, no NSwag regen, no new endpoint, no schema changes. Frontend change is i18n-only.

## Patterns / ADRs the diff must honour

- **A.1 Layered architecture** — `Core.Domain` stays third-party-package-free. The new `Attachment` record + `EmailMessage.Attachment` field live in `Core.Domain/Email/` and reference only BCL types. The SendGrid attachment wiring stays inside `Infra.Clients/SendGrid/`.
- **A.2 Feature-folder layout** — `IssueInvoice.cs` already follows the one-file shape (Command/Response/Validator/Handler nested). The Function in `Makables.Functions/Outbox/` is NOT a Features/ file (correct; it's a Function host).
- **A.4 `BusinessResult<T>`** — three new `BusinessErrorMessage` codes (`InvoiceNotYetRendered`, `InvoicePdfAttachmentDownloadFailed`, `InvoicePdfAttachmentTooLarge`). Each must be referenced via the constant, never inline literal. `InvoiceNotYetRendered` is `Error.Transient(...)`, the other two are `Error.Permanent(...)`. Each new code must appear in at least one negative-path test per must-cover-tests §9.
- **A.5 MediatR pipeline behaviors** — `GenerateInvoiceFunction.RunAsync` calls `mediator.Send(IssueInvoice.Command)`; the existing `ValidationPipelineBehavior` + `UnitOfWorkPipelineBehavior` cover validation + commit. Handler still must NOT call `SaveChangesAsync()`.
- **A.7 / TDD policy** — `OutboxEventTypes.IsInvoiceGenerate(string)` is a pure classifier (mirrors `IsEmailSend`). **This is must-cover §1-adjacent pure logic** and `EmailSendService.SendOrderPaidCustomerEmailAsync` is handler-layer orchestration. The classifier needs a test commit STRICTLY BEFORE the implementation commit (or status-log red→green entry naming the failing assertion). See "Pre-flight risks" below.
- **A.14 Error classification → retry policy** — `Error.Transient(InvoiceNotYetRendered)` MUST trip the email outbox's retry path (`SendEmailHandler.ClassifyFailure` → `OutboxErrorKind.Transient` → `OutboxRetryPolicy.NextAttempt(Transient, ...)`). This contract is already in place (`SendEmailHandler.cs:130-131`); the new code rides the existing path.
- **A.15 Provider adapter pattern** — SendGrid provider stays a thin SDK wrapper. The attachment bytes are constructed by `EmailSendService` (orchestration); the provider only encodes + calls `sgMessage.AddAttachment`. **Locked decision 7** rejects "provider downloads blob itself" — reviewer must verify no `IBlobStorageClient` dep leaks into `SendGridEmailProvider`.
- **A.20 Idempotent webhooks + UoW** — `IssueInvoice.Handler` already idempotent (step 3 short-circuit on existing invoice). `GenerateInvoiceFunction` redelivery inherits this verbatim per locked decision 5; no Function-level `ProcessedAt` tracking.
- **ADR 0015 (RDD)** — `EmailSendService` already has 5 ctor params (templates, translations, provider, urls, logger). Ticket's scope adds `IInvoiceRepository` + `IBlobStorageClient`. That puts the primary ctor at 7. **Threshold per ADR 0015 §"Risk of role-file rot": ~5 collaborators max on a handler.** Service-layer (not handler) but the rule is informally applied. See "Pre-flight risks". Order-fetch is NOT needed (see below).
- **ADR 0019 (email outbox)** — outbox is the single chokepoint into emails; locked decision 1 preserves T-0067's atomic-3-events MarkOrderPaid contract.
- **ADR 0020 (background jobs)** — new `generate-invoice` queue per "one queue per functional cluster". The dispatcher routes by event_type; separate retry budget; failure isolation.

## Pre-flight risks (HIGH severity to watch)

- **TDD commit order: `IsInvoiceGenerate` is pure-logic classifier.** Per `tdd-policy.md` + `must-cover-tests.md` §1-adjacent, the test commit MUST land BEFORE the implementation commit. Minimum: one positive case (`InvoiceGenerate` → true) + one negative (each of the 5 email event types → false; and an unknown literal → false). Reviewer will walk `git log --reverse feat/T-0069-* -- **/OutboxEventTypesTests.cs **/OutboxEventTypes.cs`. T-0069 is past the T-0067 grandfather cliff — no carve-out.
- **EmailSendService primary-ctor swell.** Current 5 deps → 7 after T-0069 (`IInvoiceRepository`, `IBlobStorageClient` added). Borderline against ADR 0015's ~5-collaborator rule. The new deps are correctly placed (orchestration, not the provider), so the alternative is collapsing two of them behind a smaller façade (e.g. `IInvoicePdfAttachmentLoader` that wraps invoice-lookup + blob-download + filename-build). Implementer brief may have left this open; reviewer flags it as a discussion item, NOT a HARD FAIL — ADR 0015 says "may not directly depend on more than ~5" with the soft "~" qualifier. If the implementer ships 7 deps, reviewer will accept with a noted concern + harvest the pattern if it recurs.
- **`OrderPaidCustomerEmailPayload` ALREADY carries `OrderNumber`.** The ticket §Scope > AppServices says: *"compute filename… extend the lookup to also fetch the Order's OrderNumber. Cheap single-row read."* This is **incorrect** — `OrderPaidCustomerEmailPayload(OrderId, OrderNumber, Email, ContactName, ...)` already pre-bakes `OrderNumber` (verified at `Core.Domain/Outbox/OrderPaidCustomerEmailPayload.cs:36`). The implementer should use `payload.OrderNumber` directly and NOT add `IOrderRepository` to `EmailSendService`. Doing so would (a) reduce the ctor swell from 7 → 6 deps, easing the ADR 0015 concern; (b) preserve the T-0067 pre-bake principle ("config drift mid-flight does not retroactively rewrite enqueued emails"). **Reviewer will request changes if an `IOrderRepository` lookup appears in `EmailSendService.SendOrderPaidCustomerEmailAsync`.**
- **`IBlobStorageClient.DownloadAsync` returns `BusinessResult<BlobDownload>` with a `Stream`, not `byte[]`.** Verified at `Core.Domain/Storage/IBlobStorageClient.cs:47`. The ticket §Scope > AppServices says: *"call `await blobStorage.DownloadAsync(BlobContainer.Invoices, invoice.PdfBlobPath, ct)` to get `byte[]`."* This is **shape-incorrect**. The handler must consume the `BlobDownload`, copy its Stream into a `MemoryStream` → `ToArray()`, and dispose the source stream (per the interface XML doc: *"The CALLER MUST DISPOSE the stream after writing the response"*). Failure to dispose = handle leak under load. Reviewer will check for `using` on the BlobDownload.Content.
- **`DownloadAsync` returns `BusinessResult<BlobDownload>` — the failure branch is a returned failure, not a throw.** The ticket's *"catch exceptions → `Error.Permanent(InvoicePdfAttachmentDownloadFailed)`"* is half-right: the handler must (a) check `!result.IsSuccess` and translate `result.Error` to `InvoicePdfAttachmentDownloadFailed`, AND (b) wrap the Stream read in try/catch because the read can still throw mid-stream after the OpenRead succeeded. Both paths converge on `InvoicePdfAttachmentDownloadFailed Permanent`.
- **OutboxDispatcher branch order: dispatcher already classifies email events.** The current `Phase 1: classify` is a binary `if (!OutboxEventTypes.IsEmailSend(evt.EventType)) → stall as Permanent`. Adding `invoice.generate` requires either (a) refactoring the classify branch into a switch (`IsEmailSend → publish-email`, `IsInvoiceGenerate → publish-invoice`, else → stall) OR (b) early-return `IsInvoiceGenerate` to a separate publish list. The OutboxDispatcherTests test `Unknown_event_type_stalls_as_Permanent_without_publishing` must still pass after the refactor — `order.shipped.send` (the test's stand-in unknown) is in neither classifier set and must still stall. Reviewer will diff the test to confirm the unknown case still asserts stall.
- **SendGrid size-error translation.** SendGrid SDK surfaces a 413 / "payload too large" as either an HTTP status (413) inside `Response.StatusCode` or as a thrown exception depending on whether it crosses the request-size sanity check at the SDK level vs. server-side. **The ticket calls out checking the exact SDK behaviour** but doesn't pin it. The implementer brief allows "classify generously if unsure". Reviewer will accept any classification that ends up as `Error.Permanent(InvoicePdfAttachmentTooLarge)` when the response is 413 or the relevant `RequestEntityTooLarge`-style status. If the implementer ships the catch as a wildcard `catch (Exception)` and classifies ALL post-retry failures as `InvoicePdfAttachmentTooLarge`, that's a regression on T-0028's existing `EmailProviderTransientFailure` / `EmailProviderPermanentFailure` classification — reviewer will request changes.
- **Race-safety: lookup-at-send-time relies on outbox retry policy.** Verified that `SendEmailHandler.ClassifyFailure` (line 126-153) maps `ErrorType.Transient` → `OutboxErrorKind.Transient` → `OutboxRetryPolicy.NextAttempt(Transient, ...)` produces a non-null retry instant for retry counts 1-6. So `Error.Transient(InvoiceNotYetRendered)` will re-deliver, NOT stall on first failure. The 1m → 5m → 15m schedule from the ticket §Technical notes matches the existing policy. **One integration concern**: locked decision 1 banks on the invoice render finishing within the first retry window. If a CI run happens to race past the 1m mark (cold-start + Functions warm-up), the second retry at 5m catches it. Test budget is 6 attempts; even a 4-attempt race fits.
- **`Attachment` record invariants.** Locked decision 8 ships `Attachment(string Filename, byte[] Bytes, string MimeType)` as a sealed record. Ticket §Scope > Domain says "Sanity-check invariants in factory if any (e.g., `Bytes.Length > 0`)." Records can be constructed via positional ctor; invariant enforcement requires either (a) an `init`-validating block in the positional record, (b) a static `Create(...)` factory + private ctor, or (c) construction-time `ArgumentException.ThrowIfNullOrWhiteSpace(filename)` + `if (Bytes.Length == 0) throw`. **The invariant should THROW at construction (entity-level invariant), not return `BusinessResult`** — `Attachment` is a value object, not a use case. Reviewer will accept either factory-method or positional-record-with-throwing-init. Reject silent-empty-bytes shipment.
- **`EmailMessage.Attachment` field nullable + back-compat.** `EmailMessage` is declared in `IEmailProvider.cs:41-51`, NOT a separate file (ticket §Scope says `Core.Domain/Email/EmailMessage.cs` — file doesn't exist; reviewer will accept adding the field to `IEmailProvider.cs` OR extracting `EmailMessage` to its own file in the same PR, but prefers the latter for hygiene). The new field MUST be optional (`Attachment? Attachment = null`) so all existing 2 call sites (auth-flow `SendAuthEmailAsync` line 137-147; order-flow `DispatchOrderEmailAsync` line 246-256) keep compiling and pass null. AC-9 + AC-10 are the regression pin.
