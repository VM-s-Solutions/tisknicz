## Ticket interpretation

T-0068b is the second half of the T-0068 L-split: the rendering + orchestration slice. It ships (1) the `IssueInvoice` one-file feature handler that orchestrates "load order → load country config → idempotency pre-check on existing invoice → allocate number → build Invoice aggregate → persist (UoW commits) → render PDF → upload blob → attach blob path"; (2) the new `Makables.Infra.PdfRendering` project containing `QuestPdfInvoiceRenderer` + two `IDocument` templates (`DokladOProdejiDocument` for `InvoicingMode.None`, `DanovyDokladDocument` for `InvoicingMode.StandardVat`); (3) the SPAYD value object on the domain side; (4) 4 new `CountryConfiguration` columns (`IssuerName`, `IssuerIco`, `IssuerDic`, `PlatformIban`) with a CZ seed migration; (5) the third `outbox.Enqueue(invoice.generate)` call inside `MarkOrderPaid.Handler` replacing the `// T-0068: enqueue invoice.generate here` marker at `MarkOrderPaid.cs:216`; (6) the T-0067 negative-pin test `Handler_does_NOT_enqueue_invoice_generate_yet` converted to a positive pin `Handler_enqueues_invoice_generate_outbox_row`; (7) ADR 0025 documenting the QuestPDF + Noto Sans + SPAYD posture per `docs/process/deliberation.md` rules; (8) i18n keys for the three new error codes plus the deferred `InvoiceBlobPathAlreadySet` key from T-0068a.

The slice DOES NOT ship the `GenerateInvoice` Function (T-0069), the customer-facing download endpoint (T-0086), or the Fee-invoice rendering (T-0101). The `Fee` path remains intentionally absent — the `QuestPdfInvoiceRenderer.RenderAsync` switch only handles `InvoiceType.Customer` paths (the only path `IssueInvoice` produces at T-0068b). `ReverseCharge` and `StrictFiscalReporting` modes return `BusinessResult.Failure(Error.Permanent(BusinessErrorMessage.InvoicingModeNotImplemented))` per locked decision 6; this is correct OOS-handling per CLAUDE.md "no mocks during build phase".

## Patterns / ADRs the diff must honour

Cited by patterns.md section number (A.N) or ADR id. Final review at PR-open will walk each row against the diff.

- **A.1 Layered architecture.** `Infra.PdfRendering` references `Core.Domain` only (read-only), never `Core.AppServices`. It MUST NOT reference EF Core. The `IInvoicePdfRenderer` interface lives in `Core.Domain/Rendering/`; the impl in `Infra.PdfRendering/`. **Verification:** grep `Core.Domain/Rendering/IInvoicePdfRenderer.cs` for non-BCL imports — must reference only `Core.Domain.Invoices` (for `Invoice`) and `Core.Domain.Configuration` (for `CountryConfiguration`) types.
- **A.2 Feature-folder layout.** `IssueInvoice.cs` lives at `Core.AppServices/Features/Invoices/IssueInvoice.cs` (NOT under `Services/`). The static-class-with-nested-types shape is mandatory per locked decision 7 + consistency-script T1. **Verification:** the file's outer declaration is `public static class IssueInvoice` containing `public sealed record Command`, `public sealed record Response`, `public sealed class Validator : AbstractValidator<Command>`, `public sealed class Handler(...) : IRequestHandler<Command, BusinessResult<Response>>`.
- **A.3 CQRS — Command vs Query.** `IssueInvoice.Command(string OrderId) : ICommand<Response>` — it mutates (creates Invoice row, attaches blob path), so it's a command. UoW pipeline commits.
- **A.4 `BusinessResult<T>` — no exceptions for expected failures.** `IssueInvoice.Handler` returns `BusinessResult<Response>`. Every failure path uses `Error.NotFound(...)` / `Error.Permanent(...)` / `Error.Transient(...)` with codes from `BusinessErrorMessage`. The renderer-throws path catches `Exception` and translates to `BusinessResult.Failure(Error.Permanent(InvoiceRenderFailed))` — caught exceptions become typed failures, not propagated up. **Centralized error codes** — `InvoicingModeNotImplemented`, `InvoiceRenderFailed`, `InvoiceBlobUploadFailed` MUST be referenced via `BusinessErrorMessage.X` constants, NEVER inline string literals. Both `Core.AppServices` and the renderer's translation glue grep clean of `"invoice.invoicingModeNotImplemented"` literals.
- **A.5 Pipeline behaviors.** Handler MUST NOT call `SaveChangesAsync()`. `UnitOfWorkPipelineBehavior` commits the Invoice row + the `Invoice.AttachPdfBlobPath` mutation atomically. **Reviewer special note:** the renderer + blob upload happen INSIDE the handler, BEFORE the UoW commit. This means a transient blob upload failure rolls back the Invoice row insert (no orphan rows). The `AttachPdfBlobPath` call modifies the tracked entity; the same UoW save flushes the `PdfBlobPath` column. **However,** the invoice number allocation via `IInvoiceNumberGenerator.NextAsync` consumes a numbering sequence value as part of the same UoW per T-0068a's design — so a renderer/blob failure also rolls back the sequence increment, preserving gap-free numbering per ADR 0009. Reviewer will spot-check that no `SaveChangesAsync` slips in.
- **A.7 Validation in Validator.** `IssueInvoice.Validator` MUST contain at least the `OrderId .NotEmpty().WithErrorCode(BusinessErrorMessage.Required)` rule + `MaximumLength(40).WithErrorCode(BusinessErrorMessage.MaxLength)` (precedent: `MarkOrderPaid.Validator` at `MarkOrderPaid.cs:65-76`). Pure logic per must-cover §5 — test-first required.
- **A.11 `Auditable`.** `CountryConfiguration` already inherits `Auditable`; the 4 new columns ride on top. `Invoice` (T-0068a) already inherits `Auditable`. No change.
- **A.13 Enforcement mode snapshot.** `Invoice.InvoicingMode` is read FROM `country.InvoicingMode` at `IssueInvoice.Handler` step 5 — the country-config row is the source of truth at issuance, and the value is then frozen onto the row. **Reviewer will verify:** `IssueInvoice.Handler` reads `country.InvoicingMode`, NOT a hardcoded `InvoicingMode.None` literal. Per T-0068a locked decision 2 + ticket §"Why renderer determinism matters", JVM YORE's MVP posture is `InvoicingMode.None`, so the CZ seed has `invoicing_mode = 'None'`. AC-2 / AC-10 require the StandardVat path to also work — verify the handler doesn't short-circuit to None.
- **A.18 Money — `long` minor units.** `Spayd.ForInvoice(string iban, long amountMinor, string currency, string variableSymbol)` takes amount in **minor units** but converts to MAJOR for the SPAYD string (per the spec, `AM:` is decimal CZK, not haléře). **Reviewer will verify:** the `amountMinor → amountMajor` conversion is half-up rounded per ADR 0003. SpaydTests AC-7 pins `AM:` formatting. Note: `CountryConfiguration.IssuerName/IssuerIco/IssuerDic/PlatformIban` are NOT monetary — no `_minor` suffix required. T6 mechanical check is therefore clear for these columns.
- **A.19 Soft-delete query filters.** `IssueInvoice.Handler` calls `IOrderRepository.GetByIdUnscopedAsync` (the outbox consumer has no audience principal). `Unscoped` already includes the soft-delete filter automatically per the global query filter; only admin reconciliation explicitly opts out via `.IgnoreQueryFilters()`. **Reviewer will verify:** the unscoped lookup is used for the outbox-triggered handler, NOT a scoped variant.
- **A.20 Idempotent webhooks / outbox consumers.** `IssueInvoice.Handler` is the outbox-consumer-side of the `invoice.generate` event. Idempotency is realised in three layers per locked decision: (a) the handler's `GetByOrderIdAsync` pre-check (T-0068a XML doc at `IInvoiceRepository.cs:118-128`), (b) the partial-unique index on `order_id WHERE is_active` is the safety net (T-0068a's `ix_invoices_order_id`), and (c) the renderer is deterministic so blob overwrite is byte-identical (T-0068a locked decision 5). **Reviewer will verify:** the handler executes the pre-check BEFORE allocating a new invoice number, otherwise the numbering sequence advances on each idempotent re-delivery and breaks the gap-free invariant.
- **ADR 0003 (Money).** SPAYD amount conversion uses minor-to-major with half-up rounding. Money columns on Invoice already shipped at T-0068a. New CountryConfiguration columns are strings, not money. **Verification:** migration SQL for `country_configurations` shows `VARCHAR(...)` for the 4 new columns, NOT `BIGINT`.
- **ADR 0009 (Numbering).** `IInvoiceNumberGenerator.NextAsync(order.CountryCode, ct)` is called inside the handler. The generator already exists from T-0068a; T-0068b is the first caller. Reviewer will verify the call is INSIDE the UoW transaction (no explicit `BeginTransactionAsync` in the handler) so a downstream failure (renderer / blob) rolls back the sequence increment. ADR 0009 §"Gap-free invariant" pins this.
- **ADR 0011 (File storage).** Blob upload goes through `IBlobStorageClient`, never via raw `BlobClient` from the Azure SDK. The blob container is `BlobContainer.Invoices`. **Reviewer will verify:** the blob path matches the ticket's documented format `invoices/{cc}/orders/{orderId}/{invoiceNumber}.pdf` (lower-case cc per ADR 0011 normalisation). Overwrite=true is acceptable per locked decision 5 (renderer is deterministic).
- **ADR 0013 (Scoped repositories).** `IInvoiceRepository.GetByOrderIdAsync` is called from the outbox consumer (unscoped context). The XML doc on T-0068a (`IInvoiceRepository.cs:118-128`) explicitly says "Unscoped — backs T-0068b's idempotency check". No new scoped methods needed.
- **ADR 0014 (Unit of Work / Admin audit log).** Same as A.5 — handler doesn't commit. Audit log entries auto-flow from `Auditable.CreatedBy/At` set by the change tracker interceptor.
- **ADR 0019 (Email — Resend) — but only orthogonally.** `LanguageCode` carried in `InvoiceGenerateOutboxPayload` so T-0069's email-attachment step can resolve `faktura-{orderNumber}.pdf` vs `invoice-{orderNumber}.pdf` filename. Mirrors T-0028 "pre-resolve language at producer" pattern. **Reviewer will verify:** the payload includes `LanguageCode` but NOT `RecipientEmail` (per ticket §"Why LanguageCode is in the outbox payload" — T-0069 resolves the email).
- **ADR 0020 (Background jobs / Outbox).** `OutboxEventTypes.InvoiceGenerate = "invoice.generate"` MUST be added. The constant matches the existing ADR 0020 routing table at line 74. **Reviewer will verify the negative case:** `IsEmailSend(InvoiceGenerate)` MUST return `false` — `InvoiceGenerate` is NOT an email event, it's a queue-routed work event that T-0069's `GenerateInvoice` Function will consume. If the implementer accidentally adds `or InvoiceGenerate` to the `IsEmailSend` chain at `OutboxEventTypes.cs:46-50`, that's a hard-fail (it would route the invoice-generate work to the send-email queue).
- **ADR 0023 (NFR) — Hot-path performance.** The handler issues several DB calls (order lookup, country lookup, GetByOrderIdAsync idempotency check, NextAsync allocation, AddAsync). All MUST propagate the `CancellationToken`. The renderer is CPU-bound (PDF assembly) — the handler awaits it on the thread pool; reviewer will verify no `.Result` / `.Wait()` on the renderer call. Blob upload propagates `ct` too.
