## Pre-flight risks (HIGH first)

### HIGH

- **HIGH-1: Complete-loop money integrity — atomic batch completion.** T-0103's settle is the headline correctness hole. The handler MUST materialize the claimed orders once (`GetByPayoutBatchIdForCompletionUnscopedAsync`, **tracked**, `Include(Maker)`), then loop `order.Complete(clock)` **in the same handler under one UoW** — no per-order `mediator.Send` (Q2 / Q-0008 MARS lesson). Reviewer verifies at PR-open:
  1. **All-or-nothing.** If ANY `order.Complete` returns non-success mid-loop, the handler surfaces the failure (`LogCritical` per §C.6) and the `UnitOfWorkPipelineBehavior` rolls back the **entire** transaction — the batch must NOT end `Completed` with some orders still `Delivered`. AC-8 names "a forced mid-loop failure persists nothing" — there MUST be an integration test that injects a mid-loop refusal and asserts the `payout_batches` row is still `Processing` AND no order flipped. (`order.Complete` only refuses if state != Delivered, which T-0102a's claim invariant prevents — so this is belt-and-braces; the test still must exist to prove the rollback wiring.)
  2. **No `SaveChangesAsync()` in the handler** — grep the handler; the pipeline is the only writer.
  3. **One DbContext, one transaction** — the tracked load + N mutations + N outbox enqueues + the audit row all ride the single pipeline commit.

- **HIGH-2: Per-maker email dedup + total reconciliation.** Group the materialized orders by `MakerId`; enqueue **exactly one** `payout.payoutSent.makerEmail` per distinct maker (not per order — Option D rejected; not one cross-maker digest — Option E rejected, that would leak cross-maker totals). Reviewer verifies:
  1. `MakerTotalPaidMinor == Σ(that maker's MakerPayoutAmountMinor in the batch)` — and this MUST reconcile with the Fee invoice + the CSV line from PR #1 (the same per-maker SUM). The unit test (handler #3: 5 orders one maker → 1 email, summed total) + integration #3 (multi-maker: A×3 + B×1 → exactly 2 rows, deserialize each payload's `OrderCount`/`MakerTotalPaidMinor`) are red-first / must-exist.
  2. The payload carries **no other maker's data** — `PayoutBatchPayoutSentMakerEmailPayload` is per-maker-scoped (`MakerId`, `MakerEmail`, `MakerTotalPaidMinor`, `BatchNumber`, `OrderCount`, `FeeInvoiceActionUrl`). Verify the `FeeInvoiceActionUrl` deep-link is `{makerAppBaseUrl}/dashboard/maker/vyplaty/{batchId}` (the T-0116 route) and carries no cross-maker id.

- **HIGH-3: Idempotency — Silent-Success state-guard at the top.** Re-calling complete on an already-`Completed` batch MUST return 200 with the **stored** facts and `AlreadyCompleted = true`, with **NO re-transition, NO order re-touch, NO email re-emit, NO second audit row** (§C.1, AC-3). The state-guard is in the **handler** (so the response can echo stored `CompletedAt`/`BankReference`), checked **before** `batch.Complete` and before the order load. Reviewer verifies: handler step ordering puts the `State == Completed` short-circuit immediately after the load (step 3, before transition); the second call's different bank-ref is **ignored** (first settlement authoritative). Integration #2 (idempotent re-call → no new outbox/audit rows, batch row unchanged) is must-exist. This is what makes the T-0104 timer/retry path safe.

- **HIGH-4: T-0112 IDOR across all three queries (the headline leak risk).** A batch holds many makers' orders; leaking another maker's payout/breakdown is the dominant risk. Each query is maker-scoped **twice** (handler resolves `makerId` from session via `IMakerRepository.GetByUserIdAsync`; projection `Where` re-filters). Reviewer verifies at PR-open:
  - **`GetMakerPayoutDetailAsync`**: the order-line projection MUST filter `o.MakerId == makerId` (not just "batch contains one of my orders") — the detail query MUST project **ONLY this maker's** lines, never the whole batch. Integration #2 (AC-3) asserts every line `o.MakerId == makerA.Id` AND none of makerB's order numbers appear AND `SUM(line) == MakerTotalPaidMinor`. The IDOR guard (`AnyAsync(o.PayoutBatchId == batchId && o.MakerId == makerId)`) returns `null` for unknown OR cross-maker — **same 404 shape, no enumeration oracle** (AC-5, Option I rejected). Hard-fail if a cross-maker batch id returns 403 (distinguishes "exists but not yours" — an oracle).
  - **`GetMakerPayoutsPagedAsync`**: `MakerTotalPaidMinor` = the per-maker SUM, **NEVER** `PayoutBatch.TotalAmountMinor`. AC-2 integration cross-checks against the DB sum. `FeeInvoiceId` scoped to `i.MakerId == makerId && i.Type == Fee` (not makerB's invoice).
  - **`GetMakerOutboxEventsForOrderAsync`**: IDOR guard `AnyAsync(o.Id == orderId && o.MakerId == makerId)` → cross-maker order returns an **empty page** (not 403, not an oracle — AC-8). And **payload non-exposure**: the projection MUST NOT name `e.PayloadJson` / `e.LastErrorCode` / `e.RetryCount` (the payload carries customer email/address/provider refs). AC-11 names a **grep gate**: `PayoutQueries.GetMakerOutboxEventsForOrderAsync` contains zero `e.PayloadJson`. AC-7 integration asserts the serialized body has no `payloadJson`/`lastErrorCode`/customer-email member. The derived `OutboxDeliveryStatus` 3-value down-projection is the only state the maker sees.

- **HIGH-5: T-0112a download IDOR + type gate.** Reviewer verifies the full lookup chain (§C):
  - The IDOR shield IS the lookup predicate — `GetForMakerReadOnlyAsync` filters `i.Id == invoiceId && i.MakerId == makerId`. A cross-maker Fee-invoice id → `404 order.notFound`, **identical** to a nonexistent id (AC-2, no oracle); blob client `Received(0)`.
  - **`InvoiceType.Fee` gate** is its own step AFTER the ownership load and returns `order.notFound` (NOT `invoice.notYetRendered`) — a maker pointing this route at a **Customer** invoice id (theirs or anyone's) gets the same 404, no leak that a Customer invoice with that id exists (AC-3). The gate MUST fire **before** the blob read (unit test 5 + integration (b) pin `Received(0)`). Hard-fail if the `Fee` gate is missing or placed after the blob download.
  - Headers: `Cache-Control: private, no-store` (NOT the label's `public, immutable` — Fee invoices carry maker PII: name, IČO/DIČ, address), `Content-Disposition: attachment; filename="faktura-{InvoiceNumber}.pdf"` through `EscapeFilenameForHeader`, ETag/304. No `Cache-Control` on any 404.
  - **Controller-direct, no MediatR** (ADR 0014 §"Handler-free read paths") — hard-fail on a `GetMakerFeeInvoice` feature (Option B rejected).

- **HIGH-6: CSV non-exposure (cross-maker PII, GDPR).** The bank CSV carries every maker's account number — operator-only. Reviewer greps the **entire diff** for any maker-facing CSV surface:
  - **Backend:** no maker-host route returns `CsvBlobPath` / the CSV blob; `MakerPayoutListItemDto` / `MakerPayoutDetailDto` carry **no** `CsvBlobPath`, **no** `BankReference`, **no** reference to the cross-maker `PayoutBatch.TotalAmountMinor` (AC-11 compile-time + grep gate).

- **HIGH-7: i18n parity (HARVESTED — zero tolerance).** Per `recurring-findings.md` row #2 (now at **count 3**, third strike fired at payout-core `csvPathAlreadySet`): every new `BusinessErrorMessage` constant MUST ship its parallel `cs-CZ` key in the same PR. This is no longer a checklist nit — it is an **automatic flag**.
  - **T-0103:** the one new code `PayoutBatchNotProcessing = "payoutBatch.notProcessing"` MUST have `'payoutBatch.notProcessing'` in `frontend/src/lib/i18n/cs-CZ.ts` (§C.10 + the i18n scope section commit it). **Auto-flag if absent.**
  - **T-0116:** every new maker UI string under `dashboard.maker.payouts.*` (list headers, state labels, breakdown headers, empty/error, download button, notFound) MUST be keyed — zero hardcoded Czech outside `cs-CZ.ts` (AC-12). ### MEDIUM

- **MEDIUM-1: `PaymentDate` → `CompletedAt` midnight-UTC derivation.** `CompletedAt = paymentDate?.ToDateTime(TimeOnly.MinValue, DateTimeKind.Utc) ?? clock.UtcNow`. No separate `PaymentDate` column (Option J rejected — one authoritative timestamp). Verify the domain test (`PaymentDate_provided_sets_CompletedAt_to_midnight_utc`) asserts `2026-06-10T00:00:00Z` exactly, and AC-2 (omitted → `clock.UtcNow`).
- **MEDIUM-2: `CompletedAt DESC` nulls-last sort.** `Processing` batches have null `CompletedAt`; under `ORDER BY CompletedAt DESC` the EF/Postgres translation sorts nulls last (in-flight batch lands after Completed ones). Acceptable at MVP (one in-flight batch). Secondary `BatchNumber DESC` is lexicographically week-ordered. Verify the EF translation actually produces nulls-last (Npgsql default for DESC is NULLS FIRST in raw SQL — confirm EF emits the intended order or an explicit `NULLS LAST`; otherwise the in-flight batch jumps to the top). **Optimizer-ping candidate.**
- **MEDIUM-3: Two-pass count + Skip/Take on the grouped payout list.** `GetMakerPayoutsPagedAsync` groups orders by `PayoutBatchId`, then `CountAsync` on the grouped set + `Skip/Take`. The GROUP BY runs twice. Confirm the `(MakerId, PayoutBatchId)` access path is indexed (the ticket asserts it is covered by existing order indexes — verify at PR-open). **Optimizer-ping** (Gate 8: new paged query). Same two-pass on the outbox-events query.
- **MEDIUM-4: `FeeInvoiceId` LEFT JOIN nullability.** A batch row created before its Fee invoices rendered (race) surfaces `null` — T-0116 hides the download CTA until it populates (AC-9: `FeeInvoiceId == null` → no button, no disabled stub). Verify the LEFT JOIN `.Select(i => i.Id).FirstOrDefault()` and that the frontend render condition is `!= null`, not a truthiness check that would also hide a valid empty-string id.
- **MEDIUM-5: Double-brace email subject (Q-0017 lesson).** The `SeedPayoutSentMakerEmailTemplate` migration writes `{{batch_number}}` / `{{total_paid}}` / `{{order_count}}` / `{{fee_invoice_url}}` verbatim. If the seed SQL is built inside a C# `$@"..."` interpolated string, `{{` collapses to `{` and the raw token reaches the recipient. Verify the placeholders survive as double-brace in the actual seeded row (AC-10) — built via non-interpolated constants or correctly escaped. cs-CZ subject `"Výplata za dávku {{batch_number}} odeslána"`, tykání body.
- **MEDIUM-6: `total_paid` server-side formatting in `EmailSendService`.** The payout-sent email renders `total_paid` via server-formatted CZK (formatCzk-equivalent). Verify the formatting strips haléře per the CZK display rule and uses the space thousands separator — and that it is done server-side in the render context, not as a raw minor-units integer in the template.
- **MEDIUM-7: Frontend money is format-only.** AC-7 names a **grep proof**: no client-side arithmetic anywhere in the `vyplaty` route. Every figure (batch total, product price, platform fee, net payout) comes from the wire and passes through `formatCzk(amountMinor, currency)` only. Verify no `+`/`-`/`reduce` over money fields in the route/helper.
- **MEDIUM-8: `OutboxDeliveryStatus` derivation correctness.** The 3-value derivation (`Processed` if `ProcessedAt != null`; `Stalled` if `NextRetryAt == null && ProcessedAt == null && LastErrorKind ∈ {Permanent, Configuration}`; else `Scheduled`) MUST be EF-translatable (runs in the projection, not in-memory). AC-9 pins all three branches. Verify the conditional translates to SQL (no client-eval warning).
