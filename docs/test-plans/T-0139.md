# Test plan — T-0139 (Apple Sign-In — server-side OAuth flow, fourth identity provider)

## Scope under test
Apple as a fourth OAuth identity provider mirroring Google (ADR 0012 + ADR
0026): `StartAppleOAuth` / `CompleteAppleOAuth`, `AppleOAuthClient` (ES256
client-secret JWT via `AppleClientSecretSigner`, `form_post` callback,
first-auth-only `user` field, `email_verified` string-vs-bool quirk),
`User.AppleSub` + `LinkAppleSub`, `apple_sub` migration, new `AuthController`
actions, and the frontend `AppleSignInButton`. Security-touching (admin
audience rejection, JWT audience enforcement, webhook-adjacent OAuth-state
verification) — no live Google controller/button exists to regress against
(flagged, not this ticket's fault).

## Preconditions
- Backend built locally; `Makables.Tests` (unit) runnable without Docker.
- `Makables.IntegrationTests` requires Docker/Testcontainers (Postgres) —
  **not available in this sandbox**; those suites were not executed here and
  must be confirmed green in CI before merge.
- Apple Developer Services ID / Team ID / Key ID / `.p8` private key are a
  manual pre-merge step (per ticket) — not required for unit-level proof.

## Gap detail (Gate 0 — concrete, with file:line)

1. **AC-3/AC-4 — `AppleOAuthClient` has no test coverage at all.**
   - Guard that's missing: no test constructs `AppleOAuthClient` and drives it
     through `ExchangeCodeAsync` (e.g. via a fake `HttpMessageHandler` or WireMock
     serving a token response + JWKS), so `ParseFlexibleBool`
     (`backend/src/Makables.Infra.Clients/Apple/AppleOAuthClient.cs:200-211`) —
     the exact method the ADR 0026 Compliance section calls out as needing a
     passing test for `email_verified` string-vs-bool — is never exercised.
   - Trigger: Apple sends `"email_verified":"false"` (string) in a real id_token;
     `ParseFlexibleBool` would in fact handle it correctly per the code read, but
     that correctness is **asserted nowhere in the test suite**, so a future
     refactor of this method could silently regress it without any red test.
   - Recommendation: add a focused unit test on `AppleOAuthClient` (constructed
     with a mocked `IHttpClientFactory`/`HttpMessageHandler` and a canned JWKS +
     id_token) asserting both the `"false"` string and boolean `false` forms, and
     the `client_secret` form field carrying the signer's JWT output — this is
     the literal AC-3/AC-4 proof requirement and is currently only proven by
     manual code reading, not by the test suite.

2. **AC-10 — no frontend test for `AppleSignInButton`.**
   - No `*.test.tsx`/`*.spec.tsx` exists for this component. A human/preview-env
     check should verify: button renders next to the Google button (or alone,
     since Google's button/controller don't exist yet — see below); clicking it
     calls `startAppleOAuth(host)` and redirects via `window.location.href` on
     success; on failure, `onError` is invoked and the mapped i18n string
     renders in the shared Alert slot (test at minimum the
     `auth.oauthNotAllowedForAdmin` / `auth.oauthInvalidState` /
     `auth.oauthEmailNotVerified` / `auth.oauthExchangeFailed` mapped strings
     actually exist in `cs-CZ` and are not the raw error code).

3. **Discovered gap, not this ticket's fault (flagging only):** Google's own
   OAuth controller endpoints and button were never wired end-to-end before
   this ticket — only `IGoogleOAuthClient`/handlers exist at the app-service
   layer, no live `google/start`/`google/callback` controller actions, no
   Google button component. Apple is therefore the **only functional OAuth
   path** in the running app right now. AC-10's "adjacent to the existing
   Google button" cannot be visually verified in a live preview because there
   is no live Google button to be adjacent to — the preview-env check should
   confirm the Apple button renders correctly on its own, and this Google gap
   should be tracked as a separate ticket/question, not silently closed by
   this ticket's scope.
