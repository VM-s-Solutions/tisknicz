# Test plan — T-0102a (CreatePayoutBatch — claim Delivered orders into an immutable weekly batch)

## Scope under test
Admin claim command `POST /api/v1/payout-batches` on `Web.Admin`: claim every
payout-eligible `Delivered` order for the default country into a new
`PayoutBatch` born `Processing`, sum `Order.MakerPayoutAmountMinor` into the
batch total, surface exclusion counts (Q3 partial-refund, Q5 no-bank-account),
the `payoutBatch.empty` guard (no row), the re-run-returns-existing-batch
idempotency (`AlreadyExisted = true`), the `payoutBatch.weekAlreadyProcessed`
week guard, the currency-homogeneity guard, the handler-written admin audit
row, atomic single-UoW claim, TZ-aware batch-number derivation, and admin
audience enforcement. The `PayoutEligibility.Classify` pure spec is the
red-first TDD surface.

Artifact generation (fee invoices, CSV, emails) is the same handler
invocation but covered in T-0102b. No admin UI (T-0118) — manual cases run
against the staging admin host via Swagger/curl with an admin JWT.

## Preconditions
- Staging backend deployed from the bundle branch; migrations applied
  (`payout_batches`, `orders`/`invoices` FK, Q-0017 fix, fee-invoice template
  seed). Blob + QuestPDF available on the preview env (artifact path runs in
  the same command — keep it green so the claim commits cleanly).
- **Admin account** with a valid admin-audience JWT (plus one customer + one
  maker JWT for the audience-rejection case).
- **Seeded Delivered orders:** at least 3 eligible across 2 makers WITH valid
  bank accounts and `RefundedAmountMinor == 0`; 1 Delivered order with
  `RefundedAmountMinor > 0` (partial refund); 1 Delivered order whose maker has
  `BankAccount = null`; 1 each of `Disputed`/`Shipped`/`Completed`/already-batched.
- DB/SQL access to inspect `payout_batches`, `orders.payout_batch_id`, and
  `admin_audit_log`.
- `Comgate N/A` here (no payment provider call on the claim path).

## Edge cases
- Single eligible order, single maker → `OrderCount = 1`, `MakerCount = 1`
  (`makerCount > orderCount` invariant never trips).
- All candidates excluded by a mix of Q3 + Q5 reasons → empty run with both
  exclusion counts > 0; verify counts are independent (an order excluded for
  refund is not also counted as no-bank).
- A maker with both an eligible AND a partially-refunded order → only the
  eligible one claimed; the maker still counts once toward `MakerCount`.
- Long-`MakerPayoutAmountMinor` sum near aggregation: confirm no overflow at
  realistic MVP scale (sanity, not a blocking case).
- Same-week re-run AFTER completion but with NEW eligible orders that arrived
  meanwhile → still `weekAlreadyProcessed` (they ride next week) — confirm
  this is intended, not a stranded-orders defect.
