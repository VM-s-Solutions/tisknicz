# Test plan — T-0103 (MarkPayoutBatchCompleted — settle a payout batch)

## Scope under test
Admin settlement command: `POST /api/v1/payout-batches/{id}/complete` on
`Web.Admin` — records the executed bank wire (`BankReference` required +
optional `PaymentDate`), drives the batch `Processing → Completed`, every
claimed order `Delivered → Completed`, and enqueues exactly **one
`payout.payoutSent.makerEmail` per distinct maker** carrying that maker's
own total — all atomically in ONE UoW (ADR 0014). Silent-Success on an
already-`Completed` re-call (no re-transition, no second email, no second
audit row). `IAdminAuditableCommand` audit (`payoutBatch.complete`,
`Notes = bankReference`). Admin-audience JWT enforced per host (ADR 0013);
fail-closed session check inside the handler.

No admin UI exists (T-0118) — manual cases execute against the staging
admin host via Swagger/curl with an admin JWT.

## Preconditions
- Staging admin backend deployed from the bundle branch; migrations
  applied (`bank_reference VARCHAR(140)` on `payout_batches`;
  `SeedPayoutSentMakerEmailTemplate` → `PayoutSentMaker` template cs-CZ +
  en-US).
- **Admin account** with a valid admin-audience JWT (and one customer +
  one maker JWT for the audience-rejection case).
- A **seeded `Processing` batch spanning ≥2 makers** (e.g. maker A ×2
  orders, maker B ×1) produced by T-0102a's claim against Delivered
  orders, with the per-maker Fee invoices + PDFs already rendered (so the
  payout-sent email's `FeeInvoiceActionUrl` deep link resolves to a real
  fee invoice).
- One already-`Completed` batch (settle one first, or seed it) for the
  idempotency case.
- Mailbox access (staging email sink) for the seeded makers.
- **Reduced test parallelism (known-env note, NOT a bundle defect):** on
  busy boxes the Testcontainers Postgres connection ceiling can be hit
  when the integration suite runs at full parallelism. Run the payout
  integration suite with
  `dotnet test --filter "MarkPayoutBatchCompleted" -- xUnit.MaxParallelThreads=2`
  to stay under the connection limit. This is an environment workaround,
  not a product issue.

## Edge cases
- `paymentDate` in the **future** → accepted (operator's value-date call,
  no validator rule); `CompletedAt` is that future midnight UTC.
- Two rapid identical settle POSTs (double-submit): the second sees the
  batch already `Completed` → Silent-Success; verify exactly one
  settlement (one transition, one set of emails, one audit row), never a
  double-email.
- `bankReference` with leading/trailing whitespace → stored `.Trim()`-ed
  (domain trims); verify the persisted value and the audit `notes` are
  trimmed.
- A claimed order that is somehow NOT `Delivered` (invariant violation) →
  `order.Complete` refuses → `LogCritical` + whole UoW rolls back (no
  half-settled batch).
- Maker FK missing at email enqueue (claimed order's maker deleted) →
  refuse to commit (AC-8 atomicity holds; surfaces the inconsistency).
