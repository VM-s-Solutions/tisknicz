# Test plan — T-0110 (DeleteUserPermanently — GDPR hard-delete + PII erasure matrix)

## Scope under test
`POST /api/v1/users/{id}/erase` on `Web.Admin`. **The single most
sensitive command in the backlog** — the ONLY place EF Core `Remove()` runs
against user data, the only PII-erasure path, genuinely irreversible. A thin
handler (load Unscoped → two gates → invoke seam → return) over the
architect-owned `IUserDataDeletionService.EraseAsync`, which stages the full
anonymize-then-hard-delete matrix in ONE unit of work; the
`UnitOfWorkPipelineBehavior` commits atomically; `AdminAuditPipelineBehavior`
records WHO erased WHOM.

Surfaces under test: the full erasure matrix e2e (User gone, RefreshTokens +
unreferenced Address hard-deleted, Order contact snapshots + Review author +
Maker PII anonymized, IČO + bank RETAINED with `IsRetainedForLegal = true`,
**Invoices byte-identical**, audit row survives referencing the deleted id);
**Gate 2 in-flight interlock** (customer-role AND maker-role orders in
`[PendingPayment, Paid, Accepted, Shipped]`) → 409, nothing mutated;
**Gate 1 retype** mismatch → 409; NO Silent-Success on re-call (→ `notFound`);
**atomicity** (forced mid-pass failure → nothing erased); admin-audience JWT
enforcement; and a **GDPR-completeness checklist** accounting for every PII
field.

No admin UI exists (T-0118) — manual cases execute against the staging admin
host via Swagger/curl with an admin JWT. **§Architect-review + security
review both required on the PR.**

## Preconditions
- Staging backend deployed from the admin-ops bundle branch; the
  `AddMakerIsRetainedForLegal` migration (`is_retained_for_legal BOOLEAN
  NOT NULL DEFAULT false` on `makers`) applied.
- **Admin account** with a valid admin-audience JWT (+ one customer and one
  maker JWT for the audience-rejection case).
- **A deletable maker-user fixture** seeded with anonymizable + retainable +
  hard-deletable records, all in SETTLED states so it is erasable:
  - 1 `Delivered` order + 1 `Completed` order (customer role), each with a
    populated contact snapshot (`ContactName` / `ContactEmail` /
    `ContactPhone`).
  - The user is also a **maker** with maker-role orders (for the maker-role
    interlock case, in a separate fixture variant those are in-flight).
  - 1 issued `Invoice` (Customer or Fee) — the byte-identical retention
    proof.
  - 1 `Review` authored by the user (review body about the maker).
  - 2 `RefreshToken` rows.
  - 1 `Address` row that is **unreferenced** by any live entity, AND (for the
    retained-address check) the maker's legal-seat `Address` still referenced.
  - Maker `RegistrationNumber` (IČO) + `BankAccount` populated,
    `IsRetainedForLegal == false`.
- A SECOND fixture variant: the same user but with one order in `Paid`
  (in-flight) — once as the **customer**, once as the **maker** on the order.
- DB access with `IgnoreQueryFilters()` capability (psql) to confirm the
  `User` row is truly gone (absent even under filter bypass) and to read
  back every matrix entity + `admin_audit_log`.
- A test seam / fault-injection hook to force a mid-pass failure inside
  `EraseAsync` (for the atomicity case) — e.g. a wrapped DbContext that
  throws after the anonymize stage but before the final `User` Remove, OR an
  integration test that injects a failing interceptor. Record the mechanism.
- **Reduced-parallelism note:** integration tests use Testcontainers
  Postgres and seed cross-entity fixtures; run with the configured xUnit
  collection serialization (reduced parallelism) so the shared seeded user /
  CZ config / invoice rows are not mutated concurrently across the bundle's
  fixtures. The erasure test in particular must own its fixture exclusively.

## GDPR-completeness checklist (every PII field accounted for)
Each row must be verified post-erasure in TC-1. A field with no disposition
is a leak — flag immediately.

| Entity.Field | Disposition | Post-erase expected | Verified |
|---|---|---|---|
| `User` (whole row + all PII columns: email, name, phone, password hash) | HARD-DELETE | row absent even under `IgnoreQueryFilters` | |
| `RefreshToken` rows (the user's) | HARD-DELETE | all gone | |
| `Address` (user's, **unreferenced**) | HARD-DELETE | gone | |
| `Address` (maker legal-seat, **referenced**) | RETAINED | still present (skip-if-referenced) | |
| `Order.ContactName` | ANONYMIZE | `"Anonymized"` | |
| `Order.ContactEmail` | ANONYMIZE | `"Anonymized"` | |
| `Order.ContactPhone` | ANONYMIZE | `"Anonymized"` | |
| `Order` (pricing / state / timestamps) | UNTOUCHED | byte-identical | |
| `Review` author projection | ANONYMIZE | `"Anonymized"` | |
| `Review` rating + body | UNTOUCHED | unchanged (about the maker) | |
| `Maker.CompanyName` + maker PII (contact) | ANONYMIZE | `"Anonymized"` | |
| `Maker.RegistrationNumber` (IČO) | RETAINED | unchanged | |
| `Maker.BankAccount` | RETAINED | unchanged | |
| `Maker.IsRetainedForLegal` | SET | `true` | |
| `Invoice` (every column) | RETAIN UNTOUCHED | byte-for-byte unchanged (Art. 17(3)(b)) | |
| `AdminAuditLogEntry` (this command's row) | SURVIVES | present, references deleted `UserId` | |

**Checklist gap to challenge:** the matrix enumerates the known PII-bearing
entities. The *real* risk (Risk §matrix-incompleteness) is a PII column that
exists but is NOT in the matrix. QA must independently grep the schema for
user-identifying columns (any FK to `users`, any `*_email` / `*_name` /
`*_phone` / `ip_address` column on entities the user touches —
e.g. `OrderMessage` author, payout-batch recipient snapshots, any cached
contact on shipping labels) and confirm each is either covered above or
provably not the data subject's PII. Record any column lacking a disposition
as a HIGH defect — leaving PII behind is a legal failure, not a cosmetic one.

## Automated cases (must-cover per tdd-policy)
Pure logic = the in-flight-state set + the anonymization transforms —
**red-first** (commit `1d772af` pins predicates before implementation
`0ff9b38` — TDD ordering verified in git log). Must-cover proof:
- `Makables.Tests/Domain/Identity/DeleteUserPermanentlyPredicateTests.cs`
  (+ Makers) — `InFlightOrderStates` contains EXACTLY
  `{ PendingPayment, Paid, Accepted, Shipped }` and EXCLUDES `Delivered`,
  `Completed`, `Cancelled`, `Refunded`, `Disputed`;
  `AnonymizeForErasure` scrubs PII, keeps IČO + bank, sets the legal flag,
  is idempotent; order-contact anonymization sets all three snapshot
  columns and touches no pricing/state column.
- `Makables.Tests/AppServices/Features/Users/DeleteUserPermanentlyHandlerTests.cs`
  — happy path invokes the seam once + returns the erased id; missing
  session → `Unauthorized` (seam NOT called); user not found → `UserNotFound`
  (seam NOT called); email mismatch → `UserDeleteConfirmationMismatch` (seam
  NOT called); email match case/whitespace-insensitive; in-flight → block
  (seam NOT called); no in-flight → seam called; **re-call → `UserNotFound`,
  NOT Silent-Success**; validator rejects empty email/reason + oversize reason.
- `Makables.IntegrationTests/Users/DeleteUserPermanentlyIntegrationTests.cs`
  — full-matrix e2e (user gone, orders anonymized, **invoice byte-identical**,
  review author anonymized, maker PII anonymized + IČO/bank retained + flag,
  refresh tokens gone, unreferenced address gone); in-flight → 409 nothing
  mutated; retype mismatch → 409 no mutation; re-call → 404 `user.notFound`
  + first audit row survives; audit row references the deleted user.

## Edge cases
- User with NO maker profile (pure customer): erasure runs; the maker-PII +
  IČO/bank steps are skipped cleanly (no null-deref). Invoices (if any)
  retained.
- User whose ONLY orders are settled (`Delivered`/`Completed`): erasure
  proceeds; contact snapshots anonymized on those settled orders.
- Address referenced by a live entity (maker legal seat) is NOT deleted even
  though the user "owns" it — the unreferenced-only rule. Confirm a shared
  address is retained.
- Atomicity under a failure DURING the seam at different points: inject the
  fault (a) before any mutation, (b) after anonymize but before hard-delete,
  (c) after the `User` Remove but before commit — all three roll back to a
  fully-intact user (single UoW boundary). At minimum cover point (b) (TC-7).
- A user with a `Disputed` order: `Disputed` is NOT in the in-flight set —
  confirm whether erasure proceeds. **Challenge:** a disputed order has money
  in escrow; if the matrix anonymizes its contact snapshot mid-dispute, flag
  whether `Disputed` should join the interlock set (raise as a question, not
  a silent pass — the ticket explicitly lists only the 4 states, but a
  disputed order is arguably "money still moving").
- `confirmedEmail` matching a DIFFERENT user's email (right format, wrong
  person) → mismatch 409 (the gate compares against THIS user's normalized
  email).

## Regression spot-checks
- After an erasure, the admin order list (`GET /admin-orders`, T-0111) still
  returns the anonymized orders with `IsActive` reflecting their state and
  `customerEmail == "Anonymized"` (the privileged view respects erasure).
- Invoice numbering remains gap-free — no invoice was deleted, so the
  sequence is intact.
- The maker aggregate / rating recompute is unaffected for OTHER makers
  (only the erased maker's PII is anonymized; its IČO-keyed tax records
  remain referenceable).
- No outbox event / email is emitted by the erasure (PM default — notifying
  a just-deleted user is pointless + a re-identification risk). Confirm the
  outbox table gained no row from the erase.
