# Test plan — T-0109 (Force-retry / acknowledge stalled outbox events)

## Scope under test
Two admin one-file commands on `Web.Admin`:
`POST /api/v1/outbox-events/{id}/retry` and
`POST /api/v1/outbox-events/{id}/acknowledge`. They nudge a single
`OutboxEvent` row's retry-state. Surfaces under test: **retry** = one-shot
"try now" via `OutboxEvent.RequeueForRetry(now)` — sets `next_retry_at = now`,
`retry_count++`, and the backoff **ladder is NOT reset** (the load-bearing
pure-logic invariant); the requeued row is re-picked by the `ProcessOutbox`
sweep; **retry on an already-processed row** → `409 outbox.alreadyProcessed`
(guard, not Silent-Success); **acknowledge** = terminal (sets `processed_at`
+ `acknowledged_at` + `acknowledged_by`, clears `next_retry_at`, removes the
row from the stalled set); **acknowledge on an already-acked row** →
Silent-Success (200, no re-mutation, original acknowledger preserved);
both `IAdminAuditableCommand` (before/after JSONB + reason); admin-audience
JWT enforcement.

No admin UI exists (T-0118 outbox triage) — manual cases execute against the
staging admin host via Swagger/curl with an admin JWT.

## Preconditions
- Staging backend deployed from the admin-ops bundle branch; no migration
  (every field `RequeueForRetry` / `Acknowledge` touch already exists on
  `outbox_events` from T-0029).
- **Admin account** with a valid admin-audience JWT (+ one customer and one
  maker JWT for the audience-rejection case).
- Seeded `outbox_events` rows reachable by id:
  - **STALLED**: `processed_at = null`, `next_retry_at = null`,
    `retry_count = 6`, `last_error_kind = Permanent`, `last_error_code` set.
  - **STALLED (mid-ladder transient)**: `processed_at = null`,
    `retry_count = 4`, a *future* `next_retry_at` (not yet due).
  - **PROCESSED**: `processed_at` set, `next_retry_at = null` (drained by
    the sweep, never acknowledged).
  - **ACKNOWLEDGED**: `processed_at` + `acknowledged_at` + `acknowledged_by
    = "admin-prior"` set.
- DB access to read back `outbox_events` + `admin_audit_log`.
- Ability to trigger / observe the `ProcessOutbox` sweep (manual function
  trigger or wait for the timer) to confirm a requeued row is re-picked.
- **Reduced-parallelism note:** integration tests use Testcontainers
  Postgres; run the bundle's integration suite with the configured xUnit
  collection serialization so seeded outbox rows are not mutated across
  fixtures concurrently.

## Edge cases
- Force-retry a **not-yet-due** transient row (future `next_retry_at`):
  "try now" overrides the backoff wait — `next_retry_at` pulled back to now,
  `retry_count` bumped (domain test #5). Confirm the handler allows this
  (the guard is only on `processed_at`, not on due-ness).
- Retry a row whose `retry_count` already == `MaxTransientAttempts`: the
  bump makes it exceed the cap; on the next failure `NextAttempt` returns
  `null` → the row stalls again immediately (one nudge, then back to the
  operator). Confirm no exception.
- Acknowledge a row that was **processed by the sweep** (not acknowledged):
  `processed_at` set, `acknowledged_by` null. The Silent-Success probe is
  `processed_at is not null`, so this Silent-Succeeds; `BuildResponse` falls
  back to `acknowledged_by ?? caller` / `acknowledged_at ?? processed_at` —
  verify the response is coherent (no null-deref).
- Double-click retry (two rapid POSTs on the same stalled id): both bump
  `retry_count` — verify the count is monotonic and no exception; the sweep
  re-picks once. Defect only if a state corruption results.
- `outboxEventId` > 40 chars → 400 (`MaxLength`); empty → 400 (`Required`).

## Regression spot-checks
- The `ProcessOutbox` sweep predicate (`processed_at IS NULL AND
  (next_retry_at IS NULL OR next_retry_at <= now)`) still behaves for rows
  NOT touched by an admin retry (T-0029 unchanged).
- The `OutboxRetryPolicy` ladder (`1m/5m/15m/1h/6h/24h`, stall after 6)
  is unchanged — T-0109 *preserves* it, does not tune it.
- A normal (non-admin) successful email/invoice/label outbox dispatch
  still reaches `MarkProcessed` and drops out of the due set.
