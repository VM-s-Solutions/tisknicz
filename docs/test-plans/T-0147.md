# Test plan — T-0147 (cookie consent banner + consent management)

## Scope under test

The first-visit cookie consent banner (`components/shared/cookie-consent-banner.tsx`)
mounted from the root layout, the `lib/consent/` category model
(`necessary` / `analytics` / `marketing`), the fail-closed `hasConsent()`
gating primitive, first-party cookie storage with a version stamp
(`CONSENT_VERSION`), the `ConsentGate` wrapper, and the "cookie settings"
entry point (footer + `/gdpr` cookies section) that reopens the customize
view pre-filled with the visitor's current choice. No backend change; no
analytics/marketing script exists yet to wrap (AC-7) — this is a pure
mechanism-plus-UI ticket.

## Preconditions

- No special environment/provider setup — purely frontend, first-party
  cookie storage, no backend or third-party dependency.
- A clean browser profile (or DevTools "clear site data") for the
  first-visit cases, since any prior manual testing leaves a
  `makables_cookie_consent` cookie behind.

## Automated cases (vitest, run on every PR — see `npm run test`)

- `frontend/src/lib/consent/__tests__/consent.test.ts`
  - `necessary` is always granted, with or without a stored choice.
  - **AC-5**: `hasConsent('analytics')` / `hasConsent('marketing')`
    default to `false` before any choice is stored.
  - `hasConsent` reflects a persisted "necessary only" choice, an
    "accept all" choice, and an exact custom combination
    (analytics-only).
  - `evaluateConsent` treats a stale-`CONSENT_VERSION` stored record,
    and a `null` record, as "no choice made" (fail-closed).
  - `writeStoredConsent` persists at the current `CONSENT_VERSION` with
    a timestamp, immediately readable back via `readStoredConsent`.
  - `readStoredConsent` tolerates a malformed cookie payload (returns
    `null`, does not throw).
- `frontend/src/components/shared/__tests__/cookie-consent-banner.test.tsx`
  - **AC-1**: first-visit renders the summary dialog with all three
    entry points ("Přijmout vše", "Pouze nezbytné", "Nastavit
    předvolby").
  - **AC-8**: zero axe WCAG 2.1 AA violations in both the summary and
    the customize view.
  - **AC-2**: "Přijmout vše" persists `{ analytics: true, marketing:
    true }` and closes the banner; `hasConsent` reflects it.
  - **AC-3**: "Pouze nezbytné" persists `{ analytics: false, marketing:
    false }` and closes the banner; `hasConsent` reflects it.
  - **AC-4**: customize view — toggling only "Analytika" on and saving
    persists exactly `{ analytics: true, marketing: false }`.
  - **AC-6**: the "cookie settings" link (`CookieSettingsLink`)
    reopens the customize view pre-filled with the prior choice;
    changing and re-saving updates `hasConsent()` on the very next
    call.
  - Regression: the banner does not render again on a subsequent
    mount once a choice has already been made (simulates the "next
    page load" case within the test's single-process constraints —
    see manual TC-2 for the real navigation case).

## Edge cases

- Version bump: manually set `CONSENT_VERSION` to a new value (or edit
  the stored cookie's `version` field via DevTools to an old number)
  and reload — the banner must reappear, i.e. a policy revision can
  force re-consent.
- Cookie stripped/blocked entirely (e.g. a privacy-hardened browser
  blocking first-party cookies) — `readStoredConsent()` returns `null`
  and the banner reappears every load rather than throwing.
- Rapid double-click on "Přijmout vše" — a single write, no duplicate
  event dispatch causing a re-render loop.

## Regression spot-checks

- `/gdpr` page's existing placeholder legal text and `Alert` disclaimer
  are unchanged — only the new "Nastavení cookies" link was added.
- Footer's existing links (`/katalog`, `/vop`, `/gdpr`, etc.) still
  render and route correctly — `FooterColumn` gained an optional
  `extra` slot, not a rewrite.
- No other route's SSR output changed — the banner is a Client
  Component island mounted once from the root layout.
