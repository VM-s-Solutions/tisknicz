# Test plan — T-0104 (RunWeeklyPayoutBatch Function — timer Monday 02:00 UTC + HTTP escape hatch)

## Scope under test
Thin ADR-0020 trigger wrapper `RunWeeklyPayoutBatchFunction`: a timer
(`%RunWeeklyPayoutBatch:Schedule%`, default `0 0 2 * * 1` = Monday 02:00 UTC,
`UseMonitor = true`) and an HTTP escape hatch
(`POST /api/payouts/run-batch`, `AuthorizationLevel.Function`), both
delegating to one dispatch-and-interpret method that sends the parameterless
`CreatePayoutBatch.Command` via `ISender` exactly once and maps the
`BusinessResult` to logs (timer) / HTTP status (escape hatch). Zero business
logic, zero new endpoints on the Web.* hosts, no NSwag regen. Idempotency is
the writer's (T-0102a) — a re-fire while a `Processing` batch is open returns
the existing batch.

Four response branches: created → Information with totals + both exclusion
counts; `AlreadyExisted` → Information "open batch returned"; `payoutBatch.empty`
→ Information (quiet week, NOT Warning); any other failure → Error with the
code (timer never throws).

## Preconditions
- Functions host deployed from the bundle branch with the writer (T-0102a/b)
  on the same branch and `RunWeeklyPayoutBatch:Schedule` present in app
  settings / `local.settings.json`.
- A valid **Function key** for the HTTP escape hatch.
- The same seeded-order fixtures as T-0102a (eligible orders with/without bank
  accounts, with/without partial refunds) reachable by the writer the Function
  dispatches.
- Log sink access (Application Insights / console) to assert log level + fields.
- `Comgate N/A` here.

## Automated cases (must-cover per tdd-policy, all on branch)

  (mocked `ISender`) — created response → `Send` called exactly once,
  Information log carries batch number + totals + both exclusion counts, no
  Warning/Error; `AlreadyExisted = true` → Information, no second `Send`, no
  Warning/Error; `payoutBatch.empty` → Information (quiet week), no
  Warning/Error; other failure code → Error with the code, timer path does not
  throw. (No pure money/numbering logic lives in the Function itself — the
  must-cover predicates are in T-0102a/T-0101; the Function tests pin
  response-branch interpretation only.)

## Edge cases
- HTTP hatch returns the SAME branch shape as the timer (single dispatch
  method) — confirm a created batch via HTTP also produces the Information log
  with exclusion counts, not just the 200 body.
- Cancellation token honored — a cancelled invocation does not partially
  dispatch (single `Send`, no loop).
- Monday 02:00 UTC coincides with the daily `CancelExpiredPendingPaymentOrders`
  sweep — both run, disjoint aggregates; confirm no interference.
- The Function logs the excluded **maker** count (Q5) and the excluded
  partially-refunded **order** count (Q3) — verify the right count is logged
  for each (per the writer response field names, not transposed).
