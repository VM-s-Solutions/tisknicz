# Test plan — T-0100 (Review entity + SubmitReview / RespondToReview)

## Scope under test
The write-side of customer reviews on the per-delivered-order grain:
`SubmitReview` (`POST /api/v1/orders/{orderId}/review`, Web.Customer),
`RespondToReview` (`POST /api/v1/reviews/{reviewId}/reply`, Web.Maker),
plus the atomic recompute-from-rows of `makers.rating_count` /
`rating_average_bp` in the SAME UoW as the review insert. The eligibility
gate (`Delivered`/`Completed` only), the partial unique index
`UNIQUE (order_id) WHERE is_active`, and the per-audience compile-time
IDOR split (`GetByIdForCustomerAsync` / `GetByIdForMakerAsync`,
cross-tenant → 404) are the security surface.

The three dashboard read queries (`GetCustomerReviewableOrders`,
`GetCustomerSubmittedReviews`, `GetMakerReceivedReviews`) are in scope as
the producers the UI consumes; the public review LIST is OUT (T-0050).
Admin moderation has **no command/endpoint** here — only the `Auditable`
soft-delete hook (an admin deactivation is exercised at the DB level in
the recompute self-healing case).

## Preconditions
- Branch backend deployed; `Add_Review_table` migration applied
  (`reviews` table, partial unique index `(order_id) WHERE is_active`,
  index `(maker_id, created_on DESC)`).
- **One customer account + one maker account**, each with a valid
  host-audience JWT. A **second customer** + **second maker** JWT for the
  two cross-tenant cases.
- A **seeded `Delivered` order** between the customer and the maker (and a
  second delivered order for the same maker for the recompute case); one
  order in a pre-`Delivered` state (e.g. `Shipped`) for the eligibility
  case; one of customer B's delivered orders against the same maker for
  the cross-tenant submit.
- **Reduced test parallelism note:** the integration suite drives
  Testcontainers Postgres + `WebApplicationFactory`; the concurrent
  double-submit + concurrent-recompute cases must run with the suite's
  reduced-parallelism collection (serialized fixture) so the
  partial-unique-index race and the maker row-lock are observed
  deterministically, not masked by container contention.
- **Admin moderation = N/A** — no admin review endpoint ships; the
  recompute self-healing case (TC-9) deactivates a `reviews` row directly
  via SQL / a seeding hook, not via an admin command.

## Edge cases
- **Concurrent recompute to the same maker** (two customers review maker
  M at the same instant): both transactions serialize on the row-locked
  Maker; the final `rating_count` equals 2 and no count is lost. Defect
  only if a count is dropped. Run under the reduced-parallelism
  collection.
- **Off-by-one in the recompute** — the just-added review must be counted
  in the stored stat. TC-1 + the recompute-correctness integration test
  pin the resulting stored value, so a read-before-flush vs
  read-after-flush off-by-one cannot ship silently.
- `rating = 5` star-only with `body: null` → valid (comment optional);
  `body: "   "` (whitespace) → stored as null.
- Maker-audience JWT **without a maker row** replies → 404
  `ReviewNotFound` (same shape as a foreign review; no existence oracle).
- `OrderId` / `ReviewId` >40 chars → 400 `MaxLength` before the repo
  read.
