# Test plan — T-0111 (Admin unscoped paged read queries — orders, invoices, audit log)

## Scope under test
Three paged, filtered, `Unscoped()` admin list queries on `Web.Admin`,
read-only (no commands, no audit rows, no new error codes):
- `GET /api/v1/admin-orders` — all orders cross-tenant, filters
  state / country / makerId / customerEmail, sorted `CreatedAt DESC`,
  privileged DTO (carries `CustomerEmail` + `MakerName`, no GDPR redaction),
  `.IgnoreQueryFilters()` so soft-deleted/anonymized rows surface.
- `GET /api/v1/admin-invoices` — all invoices, filters
  type / country / recipient / dateRange; keeps the soft-delete filter.
- `GET /api/v1/audit-log` — admin audit entries, filters
  adminUserId / actionCode / targetEntity / dateRange; list DTO OMITS
  `BeforeJson`/`AfterJson`.

This is also the **verification harness** for the bundle's three mutations
(T-0109/T-0108/T-0110 assert their side effects through these endpoints).
`security_touching: true` — the `Unscoped()` reads must be reachable ONLY
from `Web.Admin` and the privileged `CustomerEmail` exposure is deliberate.

No admin UI exists (T-0118) — manual cases execute against the staging admin
host via Swagger/curl with an admin JWT.

## Preconditions
- Staging backend deployed from the admin-ops bundle branch; no migration,
  no new error codes, no i18n keys (read-only ticket).
- **Admin account** with a valid admin-audience JWT (+ one customer and one
  maker JWT for the audience-rejection case).
- **Seeded multi-tenant data:** orders for customer A + customer B under
  makers X + Y (cross-tenant proof); at least one soft-deleted/anonymized
  order (mimics a T-0110 erasure, `IsActive == false`); Customer + Fee
  invoices across ≥ 2 countries with known recipient names + issue dates;
  ≥ 3 `admin_audit_log` entries with mixed `action_code`s, `admin_user_id`s,
  `target_entity`s, and timestamps (e.g. seeded by running an `order.refund`
  / `country.update` / `outbox.retry` in the same fixture run).
- DB access to confirm `totalCount` against the seeded population and to
  read SQL logs (the two-round-trip / `AsNoTracking` / `IgnoreQueryFilters`
  assertions).
- **Reduced-parallelism note:** integration tests use Testcontainers
  Postgres; run with the configured xUnit collection serialization so the
  seeded cross-tenant population is stable while the list assertions read it
  (concurrent mutation fixtures would change `totalCount` mid-assert).

## Edge cases
- Empty result set (filter matches nothing) → 200 with `TotalCount == 0`,
  NOT 404 (an empty admin list is success, not a domain failure).
- `pageSize == 1` and `pageSize == 50` → accepted (inclusive bounds); `0`
  and `51` → 400.
- `customerEmail`/`recipient` `ILike` with a SQL-wildcard-looking input
  (e.g. `%`) — confirm the input is parameterized (no injection / no
  unexpected match-all). Flag if a literal `%` returns every row.
- Date range with only `dateFrom` set (open-ended upper) and only `dateTo`
  set (open-ended lower) → each applies as a one-sided bound; the inverted
  check only fires when BOTH are set and `from > to`.
- A `country` filter of length != 2 → 400 (`Length(2)`, ISO-3166-1 alpha-2).
- Pagination stability: with rows sharing a `CreatedAt`, the
  `ThenByDescending(Id)` tie-breaker keeps page boundaries stable across
  two consecutive page requests (no row appearing on both page 1 and 2).
- An anonymized (post-T-0110) order row: `CustomerEmail == "Anonymized"`,
  `IsActive == false` — surfaces correctly (the reconciliation use case).
