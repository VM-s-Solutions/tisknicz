# Test plan — T-0102b (Payout batch artifacts — per-maker Fee invoices + bank CSV + fee-invoice maker emails + admin CSV download)

## Scope under test
Financial artifacts generated inside the `CreatePayoutBatch` handler via
`IPayoutArtifactService.GenerateAsync`: one `InvoiceType.Fee` invoice per
maker per batch (shared gap-free FV-CZ sequence, DUZP = batch creation date,
`PayoutBatchId` set / `OrderId` null), QuestPDF fee PDF in the `invoices`
container, the bank-transfer CSV behind `IPayoutCsvFormatter` (frozen golden
columns, UTF-8 BOM, CRLF, semicolons, VS = batch-number digits), the
set-once `PayoutBatch.CsvBlobPath`, the admin CSV download endpoint
`GET /api/v1/payout-batches/{id}/csv`, the `payout.feeInvoice.makerEmail`
outbox + `EmailSendService` branch (lookup-at-send PDF attachment), and the
artifact-failure re-entrancy contract (re-run completes missing artifacts
with no duplicate invoices).

`security_touching: true` — legally immutable Fee invoices + the payment file
an operator uploads to a bank. No admin UI (T-0118) — manual cases run against
the staging admin host via Swagger/curl with an admin JWT.

## Preconditions
- Staging backend deployed from the bundle branch; migrations applied
  (`SeedPayoutFeeInvoiceEmailTemplate` cs-CZ tykání + en-US, double-brace
  subjects; Q-0017 fix; `payout_batches` + FK).
- **Blob storage + QuestPDF available on the preview env** (artifacts run in
  the claim command; both must be live for the CSV/PDF paths to complete).
- **Admin account** with admin-audience JWT (plus customer + maker JWT for
  audience rejection).
- **Seeded Delivered orders:** ≥ 2 makers WITH validated bank accounts, each
  with ≥ 1 claimable order; one maker whose company name **starts with `=`**
  (formula-injection probe — see TC-12). Known `PlatformFeeAmountMinor` per
  order so fee sums are predictable.
- Mailbox/outbox access for the seeded makers (staging email sink) and a way
  to inspect `invoices`, `outbox`, and blob contents.
- `Comgate N/A` here.

## Edge cases
- Single maker, single order → one Fee invoice, one CSV row, VS still derived.
- Maker company name at exactly 140-char message boundary (with batch-number
  prefix) → truncated cleanly, no mid-codepoint cut on multi-byte Czech chars
  (verify truncation is by char not byte — diacritics).
- `AttachCsvBlobPath` idempotent same-value retry on re-run (deterministic
  formatter) → Success; a different value → `payoutBatch.csvPathAlreadySet`.
- Amount with `MakerPayoutAmountMinor` summing to a value whose minor part is
  `0` → `1234.00` not `1234` or `1234.0`.
- VS digit run > 10 (defensive — if batch-number format ever changes) → last
  10 digits kept.
- Fee invoice for a maker with a VAT id vs without → recipient `RecipientVatId`
  populated/null correctly; InvoicingMode.None keeps VAT zero regardless.

## Defects found
- **Candidate (TC-12) — CSV formula injection not neutralized.**
  `GenericPayoutCsvFormatter` writes the maker company name into `message`
  (and the formatter is the bank-file source) without prefixing/escaping
  cells that begin with `=`, `+`, `-`, `@`, tab, or CR. A maker-controlled
  company name starting with `=` becomes an executable formula when the
  operator opens the `.csv` in a spreadsheet. No automated test covers this.
  Confirm on the preview deploy and file against T-0102b; the fix is a
  formatter-level neutralization (prefix `'`) + a red test. Surfaced for the
  Reviewer — QA does not approve.
