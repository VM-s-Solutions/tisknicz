# Test plan — T-0105 (RefundOrder + Comgate RefundAsync + refund email)

## Scope under test
Admin refund command: `POST /api/v1/admin/orders/{orderId}/refund` on
`Web.Admin` — full + partial refunds with cumulative
`refunded_amount_minor`, provider-first ordering (Comgate `/v1.0/refund`
BEFORE any mutation), Completed-state acknowledgement gate, Silent
Success on re-refund, `order.refunded.customerEmail` outbox + template,
admin audit row, admin-audience JWT enforcement.

No admin UI exists (T-0118) — manual cases execute against the staging
admin host via Swagger/curl with an admin JWT.

## Preconditions
- Staging backend deployed from the bundle branch; migrations applied
  (`refunded_amount_minor`, `OrderRefundedCustomer` template seeds
  cs-CZ + en-US).
- **Admin account** with a valid admin-audience JWT (and one customer +
  one maker JWT for the audience-rejection case).
- Seeded orders reachable via Comgate **sandbox** (`TestMode = true`)
  with real `PaymentProviderRef`s: one Paid, one Completed, one
  Refunded, one PendingPayment (no ref), one Cancelled.
- Mailbox access for the seeded customer (staging email sink).
- **GO-LIVE MANUAL ITEM (not executable in CI):** Comgate sandbox
  `/v1.0/refund` semantics on sandbox transIds must be verified by hand
  before production cutover (ticket Risk §3 — integration suite uses
  `FakeComgatePaymentProvider`, so no automated coverage of the real
  gateway exists). Record the sandbox transId + response code here when
  executed.

## Edge cases
- `amountMinor = 1` haléř partial (smallest unit) then exact remainder.
- Two rapid identical partial POSTs (double-submit): both may succeed by
  design (no idempotency key, Alternatives G) — verify cumulative never
  exceeds total and remaining cap holds; defect only if it does.
- Refund POST with `amountMinor: 0` / negative → 400 validation (never
  reaches the domain ArgumentException).
- Reason at exactly 2000 chars accepted; 2001 rejected.
